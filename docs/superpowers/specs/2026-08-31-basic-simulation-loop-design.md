# God Simulation 基础循环设计规格

状态：已确认，进入实现

日期：2026-08-31

目标平台：本地浏览器

实现语言：TypeScript

## 1. 目的

本规格定义全新 God Simulation 项目的底层架构，以及第一个可玩的基础循环。

这个里程碑不追求完整内容，而是证明下面这条因果链能够真实运行：

```text
角色需要作决定
-> 世界冻结，模型根据角色实际知道的内容选择目标
-> 玩家放行，或由自动放行策略继续
-> 程序负责寻路、开门、移动和物件交互
-> 角色只在实际看见、接触或感觉到变化后更新认知
-> 程序能自动解决的问题继续处理
-> 程序无法继续原目标时，角色重新思考，世界再次冻结
```

模型只负责角色决策、对话文本和以后需要的认知提炼。除此以外，世界事实、规则判断、空间计算、动作执行、冲突裁决、时间推进和保存都由程序负责。

## 2. 首个里程碑范围

### 2.1 必须完成

- 在本机启动浏览器客户端、本地主程序和独立模拟进程。
- 加载一张连续的小住宅地图，包含有名称的房间、墙、门、冰箱和马桶。
- 加载 Alice、Bob 两个角色插件实例和住宅物件插件。
- 使用 `Pixel 16 Interiors` 作为地图与家具主素材，使用 `MemaoCharacterSpritePack` 作为角色素材。
- 世界以固定模拟步推进，渲染帧率不能改变模拟结果。
- 世界开始时因角色需要初次决策而冻结。
- 多个需要决策的角色可以同时等待模型响应。
- 模型只收到该角色的身体感觉、主观认知、相关记忆和实际可选目标。
- 模型返回结构化高层目标，程序将其展开为寻路、自动开门、接近和使用等动作。
- 角色能够移动、等待、观察、开门、关门、锁门、解锁、经过未锁的门、使用冰箱和使用马桶。
- 角色内急随世界时间变化；使用马桶能够通过物件效果降低内急。
- 冰箱具有占用状态，两个角色不能同时使用同一个交互位置。
- 角色不能凭数据库或完整世界状态知道门锁和家具占用。
- 寻路发现门被锁后先自动尝试其他路线；所有自动办法失败后才请求角色重新决策。
- 角色看见目标冰箱被占用，或亲自尝试使用被拒绝后，才形成冲突认知。
- 只有角色必须重新决策时才产生玩法暂停。
- 玩家可以打开或关闭“决策审查”。开启时需要查看并放行；关闭时所有本轮必要决策准备好后自动继续。
- 模型、插件、协议或存储错误必须显示并写开发日志，由玩家选择重试，禁止伪装成功。
- 使用固定模型响应的无界面场景测试完整复现基础循环。
- 真实免费模型可以手动运行，但不作为自动测试是否通过的条件。

### 2.2 明确延期

以下内容不进入首个里程碑：

- 玩家修改整个世界、强制意图或编辑记忆的完整上帝工具。
- 时间线回滚、分支比较和历史编辑界面。
- 社交邀请、持续对话、关系变化和多人会话。
- 饥饿、疲劳、情绪等完整生活需求；首版只接通内急这一条链路。
- 长期记忆总结、遗忘、向量检索和 Reflection。
- 地图编辑器、插件管理器和游戏内安装插件。
- 插件热替换、插件安全沙箱和恶意插件兼容。
- 桌面打包、云端服务、多人联机和移动端适配。
- `e3c0566aa67b878e` 手绘素材主题。
- 完整动画、音效和最终美术打磨。

这些延期功能不能迫使首版重写底层。相应边界和扩展入口仍须在架构中保留。

## 3. 不可破坏的规则

### 3.1 唯一权威世界

模拟进程内存中的 `WorldState` 是当前世界唯一可写事实来源。

- 浏览器只有只读显示数据。
- 本地主程序不保存第二份可写世界。
- 模型只看到角色主观上下文。
- 插件只返回查询答案或效果建议。
- SQLite 只保存重要结果、快照和调用记录，不参与每个模拟步的裁决。

### 3.2 模型只决定，不执行

模型可以决定“去使用马桶”“等待冰箱空闲”或“改做其他事情”，但不能：

- 宣布已经到达目标。
- 宣布门已经打开。
- 宣布物件已经使用成功。
- 自己计算碰撞、视线、距离和路径。
- 直接修改角色、物件或数据库字段。
- 决定世界何时暂停或恢复。

模型结果必须通过版本化结构校验和当前世界校验，才能成为角色准备执行的目标。

### 3.3 暂停只由角色思考引起

门被锁、家具被占用、动作子步骤完成和普通领域事件都不会自行暂停世界。

正确顺序是：

```text
世界事实变化
-> 角色实际感知到变化
-> 新认知与当前目标冲突
-> 程序尝试所有明确的自动处理
-> 确实需要角色选择新目标
-> 产生 DecisionRequested
-> 全局冻结并开始角色思考
```

技术故障使用独立的 `TECHNICALLY_BLOCKED` 状态。它会停止推进以保护数据，但不能伪装成角色思考或游戏事件。

### 3.4 有限感知

任何角色知识都必须能追溯到以下来源之一：

- 进入实际视野的可观察状态。
- 听觉范围内的声音事件。
- 距离或接触触发的身体反馈。
- 主动交互的成功或失败结果。
- 角色自身身体状态形成的感觉。
- 已经拥有的记忆。

客观状态改变不能直接写入所有角色认知。

### 3.5 确定性

- 模拟采用固定 `100ms` 世界步，即每秒 10 个模拟步。
- 渲染可以独立运行并在两个世界状态之间插值。
- 模拟内部时间使用整数世界步，不使用系统时钟推进规则。
- 位置和动作进度使用整数单位，避免跨平台浮点误差影响重放。
- 所有随机选择来自保存在世界状态中的种子，模拟包中禁止直接调用 `Math.random()`。
- 同一初始状态、插件版本、命令、模型采用结果和随机种子必须得到同一结果。

## 4. 技术栈

- Monorepo：pnpm workspace。
- 语言：严格模式 TypeScript，ESM。
- 浏览器应用：React + Vite。
- 地图渲染：PixiJS，像素素材使用 nearest-neighbor 放大。
- 本地 HTTP 与 WebSocket：Fastify 及其 WebSocket 支持。
- 模拟隔离：Node.js 独立子进程，通过类型化 IPC 通信。
- 边界校验：Zod。
- 数据库：SQLite + better-sqlite3 + Kysely。
- 模型接入：OpenRouter 的 OpenAI 兼容接口，通过统一 Model Gateway 调用。
- 空间算法：使用 `rot-js` 的网格 A* 与视野算法，通过项目自有接口适配，插件规则仍决定格子是否可走或透明。
- 单元与场景测试：Vitest。
- 浏览器端到端测试：Playwright。
- 静态规则：ESLint、TypeScript project references 和依赖图检查。

`free_model.local` 只由本地主程序读取，必须加入 `.gitignore`。密钥、完整授权头和模型原始请求不得输出到普通日志。

## 5. 进程结构

```text
Browser
  React UI + PixiJS
       |
       | HTTP / WebSocket
       v
Local Server
  会话协调、模型请求、数据库写入、状态推送
       |
       | 类型化 IPC
       v
Simulation Worker
  权威世界、固定步执行、插件、感知、决策门
```

### 5.1 Browser

负责：

- 显示地图、角色、目标、思考状态和暂停原因。
- 发送开始、停止、放行、切换审查模式和重试等命令。
- 保存只与界面有关的临时选择状态。

禁止：

- 持有可写 `WorldState`。
- 直接导入模拟内核。
- 直接访问 SQLite 或模型接口。

### 5.2 Local Server

负责：

- 启动和关闭模拟子进程。
- 提供本地 HTTP 与 WebSocket。
- 维护模型请求生命周期、超时、取消和重试。
- 将模型请求交给 OpenRouter，并将响应送回对应模拟请求。
- 作为 SQLite 单写者保存语义事件、快照和已采用的模型结果。
- 把模拟进程产生的只读 `ViewModel` 推送给浏览器。

禁止：

- 自己实现寻路、感知、家具规则或暂停判断。
- 根据模型文本直接修改世界。

### 5.3 Simulation Worker

负责：

- 持有唯一权威世界。
- 加载世界锁定的插件版本。
- 按固定顺序运行模拟步。
- 处理空间查询、物件交互、动作推进、感知和决策门。
- 产生需要持久化的事件和关键快照。
- 检查模型响应是否仍属于当前请求和当前世界版本。

世界冻结时，模拟步不推进，但进程仍能响应查询、模型结果、重试和关闭命令。

### 5.4 过期模型响应

每个模型请求包含：

- `requestId`
- `agentId`
- `worldId`
- `worldVersion`
- `decisionCycleId`
- `schemaVersion`
- `pluginLockHash`

任一字段不匹配当前等待请求时，响应不能进入世界。它可以保存为诊断记录，但不能形成角色目标。

## 7. 世界与地图

### 7.1 静态地图

地图是经过 Zod 校验的 JSON 数据，不是 TypeScript 代码。以后地图编辑器仍读写相同格式。

地图定义包含：

- 稳定地图 ID 和格式版本。
- `16x16` 像素基础格尺寸。
- 宽度、高度和地板图层。
- 房间或区域的稳定 ID、名称和格子集合。
- 物件实例的稳定 ID、插件定义 ID、位置、朝向和初始状态。
- 角色出生点。
- 使用的插件版本与资源 ID。

整栋住宅是一张连续地图。房间是有语义名称的格子区域，不是互相传送的独立场景。

### 7.2 空间放置

- 地板主要负责外观和区域标记。
- 墙、门和家具是插件物件实例。
- 普通家具可以占据一个或多个格子。
- 墙和门可以占据格子边界。
- 角色逻辑占位以脚下格子为准，角色图片以脚底中心作为锚点并可超出格子。
- 绘制锚点、图层、遮挡和碰撞分别声明，不能从 PNG 像素自动推断规则。

### 7.3 统一空间入口

寻路、碰撞、视线、距离、占用和交互位置必须使用同一套空间查询入口。插件通过能力声明提供：

- 是否阻挡移动。
- 是否阻挡视线。
- 所占格子或边界。
- 可交互站位。
- 当前状态下的空间变化。

关闭且未锁的门可以被路径计划视为带有自动开门步骤的可通过位置。锁门状态是否进入某个角色的计划，取决于该角色是否已经知道它被锁。

## 8. 插件架构

### 8.1 运行方式

- 插件使用 TypeScript 编写，构建为本地 ESM JavaScript 后由 Simulation Worker 动态加载。
- 项目不把第三方插件当安全边界；插件是本机受信任代码。
- 官方物件与官方角色也必须使用同一公开 SDK，禁止核心内部写一套特殊后门。
- 插件只在世界启动或加载存档时加载。
- 世界运行期间不热替换插件。
- 世界锁定插件 ID、语义版本、状态版本和构建文件指纹。
- 不匹配锁定信息时拒绝加载并进入技术阻塞，不能悄悄使用另一个版本。

### 8.2 统一外壳与可选能力

所有物件定义包含：

- 稳定 ID、版本、显示名称和标签。
- 状态 Schema 与默认状态。
- 图片或图集资源 ID、绘制锚点和图层。
- 放置方式与占地信息。
- 提供的可选能力。

能力按需组合，不建立包含所有家具方法的巨型接口。首版能力包括：

- `movement-blocker`
- `vision-occluder`
- `interactable`
- `occupiable`
- `lockable`
- `need-effect-provider`

墙不需要实现马桶接口；马桶不需要实现门锁接口。

实现 `interactable` 的物件可以注册多个具有稳定 ID 的交互，例如门可以同时提供 `open`、`close`、`lock` 和 `unlock`。每个交互分别声明触发方式、可见条件、开始条件、动作时长、占用槽位和结果建议，中央入口不按物件名称写条件分支。

### 8.3 状态归属

插件定义状态结构和处理规则，世界持有每个物件实例的当前状态。

插件处理时只能读取：

- 自身只读状态。
- 经过裁剪的角色投影。
- 当前触发所需的最小世界上下文。

插件返回：

- 接受或拒绝。
- 结构化原因。
- 对自身状态的建议变化。
- 对角色或其他对象的效果建议。
- 动作持续时间和身体槽位要求。
- 应产生的可感知结果建议。

所有建议由世界统一校验、裁决并一次性提交。插件不能直接写世界、数据库或另一实例。

### 8.4 角色插件

角色插件定义：

- 稳定角色定义 ID。
- 背景、性格、价值偏好、语言和思考风格。
- 初始记忆。
- 角色视觉资源和动画表。
- 可选的身体状态规则、提示词材料和记忆提炼器。

世界实例保存位置、内急、当前目标、动作进度、主观知识和记忆。角色插件不能保存第二份运行状态。

## 9. 触发方式与消息线路

### 9.1 六种触发来源

物件和角色状态只通过以下来源被唤起：

1. 系统询问：寻路、碰撞、视线和当前可用交互。
2. 主动操作：角色或玩家尝试使用、打开、锁定或等待。
3. 位置变化：进入、离开、靠近、接触或踩上范围。
4. 感知变化：首次看见、失去视线或听见事件。
5. 状态越线：内急从普通进入紧急状态等。
6. 定时触发：动作完成或效果到期；使用登记的世界时刻，不向所有插件广播每个模拟步。

### 9.2 三条消息线路

所有跨模块消息使用带 `type`、稳定 ID、版本和因果 ID 的 Zod 判别联合，不使用无类型字符串总线。

#### Command

请求改变某件事。Command 不是事实，只有校验并提交成功后才产生 Event。

示例：

- `ReleaseExecutionCommand`
- `UseObjectCommand`
- `RetryDecisionCommand`

#### Query

只读取或计算当前情况，不能改变状态，通常不保存。

示例：

- `GetWorldViewQuery`
- `VisibilityQuery`
- `AvailableInteractionsQuery`

#### Event

表示已经提交的事实。重要 Event 进入内存事件流，并由本地主程序持久化。

示例：

- `ActionStartedEvent`
- `ObjectOccupiedEvent`
- `NeedChangedEvent`
- `DecisionRequestedEvent`
- `IntentAcceptedEvent`

命名规则：操作使用动词请求语气，事件使用已经发生的语气；文件直接体现消息含义，例如 `release-execution.command.ts`。

## 10. 基础循环状态机

### 10.1 顶层状态

```text
THINKING
  世界时间冻结，等待本轮必要角色的模型结果

READY_FOR_RELEASE
  仍属于同一次思考冻结；仅在决策审查开启时等待玩家

RUNNING
  世界按固定步推进

TECHNICALLY_BLOCKED
  技术错误导致安全停止，等待明确重试或退出
```

只有 `RUNNING` 可以增加世界时间。

### 10.2 决策周期

1. `decision-gate` 确定哪些角色确实需要选择新目标。
2. 保存所有角色当前动作和进度。
3. 世界进入 `THINKING`，世界时间保持不变。
4. Simulation Worker 为每个目标角色构建独立的主观认知输入。
5. Local Server 并发调用模型。
6. 每个结果通过请求身份、结构和当前世界能力校验。
7. 本轮所需角色全部准备完成后：
   - 审查开启：进入 `READY_FOR_RELEASE`。
   - 审查关闭：自动提交放行命令。
8. 新目标转为初始动作，未受影响角色保留原动作进度。
9. 世界进入 `RUNNING`。

首版每个决策周期统一等待本轮所有必要角色准备完成，不允许模型响应先后顺序决定谁先获得额外世界时间。

### 10.3 何时请求思考

- 世界开始，角色还没有目标。
- 一个高层目标已经完成，需要选择下一个目标。
- 当前目标经过明确的自动恢复后仍无法继续。
- 角色实际感知到的新事实使当前目标前提失效。
- 角色身体状态跨过必须重新选择的紧急阈值。
- 模型目标通过格式校验但不符合当前世界能力，错误反馈后需要重试决策。

普通子动作完成、路径替换、自动开门、无关感知和远处未感知事件不请求思考。

## 11. 目标、动作与自动执行

### 11.1 三个层次

- `Goal`：角色想达到的高层结果，例如使用马桶。
- `ActionPlan`：程序根据目标和角色知识生成的可恢复执行计划。
- `Action`：当前正在推进的移动、开门、等待或使用动作。

模型只生成 `GoalProposal`，不生成逐格路径或任意脚本。

### 11.2 身体槽位

数据模型保留 `HEAD`、`HANDS`、`BODY` 三个槽位，首版主要接通 `BODY` 和必要的 `HANDS` 操作。

- 移动占用 `BODY`。
- 开门和使用物件占用 `HANDS`，并可以要求 `BODY` 位于交互点。
- 等待可以占用 `BODY` 或由目标策略声明为空闲。
- 同一槽位不能同时执行两个动作。

槽位动作完成不会自动暂停；只有其所属高层目标需要新决定时才请求思考。

### 11.3 门锁示例

```text
角色沿已知路线移动
-> 别人把门锁上，世界继续
-> 角色到门前，程序自动尝试开门
-> 门返回锁定结果，角色此时才知道
-> 程序根据更新后的角色知识重新寻路
-> 有替代路线：继续原目标
-> 无替代路线：目标无法继续，请求角色思考并冻结世界
```

## 12. 感知、冲突和角色知识

### 12.1 感知快照

角色决策时获得 `PerceptionSnapshot`，内容仅包括：

- 当前身体感觉。
- 当前所在区域及已知相邻区域。
- 实际看见的人、物件和它们公开的可观察状态。
- 实际听见或接触到的事件。
- 当前目标、动作进度和具体失败原因。
- 由这些信息导出的当前可选目标与交互。

### 12.2 可观察状态由插件控制

物件内部状态不等于角色能看见的状态。

- 冰箱可以公开“正在被 Bob 使用”，但只有视线触及后才进入 Alice 的认知。
- 门的锁定状态可以在尝试开门失败时返回，不必在远处直接可见。
- 墙通过只读视线查询返回遮挡贡献。

### 12.3 冰箱冲突示例

```text
客观事实：Bob 已占用冰箱
Alice 看不见冰箱：仍认为目标可用，世界不暂停
Alice 进入视野：感知到 Bob 与占用状态
新认知与“使用冰箱”目标冲突
程序没有唯一自动答案
Alice 请求思考，世界冻结
模型决定等待、放弃或选择其他目标
```

冲突属于具体角色。没有感知到这一事实的第三个角色不能同步获得知识。

## 13. 需求、提示词和记忆

### 13.1 内急状态

- 内急是世界持有的角色身体状态。
- 它按世界时间确定性增长。
- 插件将连续数值投影为角色能感觉到的等级。
- 只有等级越线时产生新的身体感知，避免每步重复事件。
- 紧急阈值会使角色重新评估当前目标。
- 马桶使用完成后返回降低内急的效果建议，由世界提交。

需求提供压力，但不直接规定角色必须做什么；最终目标由模型选择。

### 13.2 提示词固定顺序

1. 不可被插件覆盖的世界规则和输出协议。
2. 角色背景、性格和表达方式。
3. 当前身体感觉。
4. 当前目标、动作进度和未完成事项。
5. 本次选出的相关记忆。
6. 当前实际感知到的人、物和事件。
7. 当前真正可选的目标、对象和参数范围。
8. 本次需要思考的具体原因。

每部分具有明确标签和大小预算。插件不能把自身文本插入核心规则之前。

### 13.3 首版记忆

首版只实现可追溯的即时记忆：

- 每条记忆引用原始 Event ID。
- 记录角色从什么感官或交互获得信息。
- 原始事件和记忆不能被模型摘要覆盖。
- 提示词按新近度和与当前目标的直接关系做简单筛选。

长期总结保留 `MemoryExtractor -> MemoryProposal -> MemoryFormed` 接口，但不在首版调用模型执行。

## 14. 地图与物件互动流程

### 14.1 只读查询

```text
感知或寻路提出 Query
-> 空间索引找到可能相关的物件
-> Interaction Router 调用对应插件能力
-> 插件返回只读答案
-> 查询系统聚合结果
```

视线射线、路径预览和每步距离不进入数据库。

### 14.2 状态改变

```text
角色 Action 提出 Command
-> Interaction Router 找到目标插件
-> 插件返回 EffectProposal
-> EffectArbiter 校验距离、占用、权限、槽位和冲突
-> EffectCommitter 一次性更新权威世界
-> 产生已经发生的 Event
-> 感知、记忆、界面和存储消费 Event
```

同一世界步多人竞争同一资源时，先按实际到达世界步排序；完全同一世界步到达时，使用保存于世界状态的确定性仲裁值选择先后，并把选择原因记录到事件中。

## 15. 浏览器界面

采用已经确认的 A 方案“导演工作台”。

### 15.1 桌面布局

- 顶栏：世界名称、当前状态、世界时间和决策审查开关。
- 左侧：角色列表、各自目标与运行状态；区域列表作为次要导航。
- 中央：PixiJS 地图、角色、路径、目标和当前交互状态。
- 地图上方：当前思考原因或技术阻塞原因。
- 右侧：选中角色的概况、实际感知和即时记忆。
- 底部：首版显示当前事件序列和放行控制；未来在同一区域扩展为分支时间线。

### 15.2 基本交互

- 单击角色或地图物件进行选择。
- 空格键和播放按钮执行放行。
- 决策审查开关只控制模型结果准备好后的最后一步，不改变思考期间的冻结。
- 技术错误显示错误种类、关联请求和重试按钮。
- 开发环境可以打开结构化日志，但正常玩法信息不能要求玩家阅读日志才能理解。

首版以桌面浏览器为主要目标，最低设计视口为 `1280x720`。窄视口可折叠右侧检查器，但不为手机重新设计操作流程。

## 17. 数据保存

运行时世界始终在内存中。首版数据库只保存：

- 世界和会话元数据。
- 插件锁定信息。
- 已提交的重要 Event。
- 进入思考冻结时的完整可恢复快照。
- 已采用的模型请求摘要、响应和 Schema 版本。
- 技术错误与重试关系所需的结构化记录。

首版不保存：

- 每个渲染帧。
- 每次视线计算。
- 可重算的路径预览。
- 插件查询中间结果。
- 未被采用的过期模型响应，诊断模式除外。

完整时间分支功能延期，但快照和 Event 必须已经带稳定父序列、世界版本和因果 ID，使以后加入 Timeline 不必改变事件格式。

## 18. 错误处理

### 18.1 模型错误

包括网络失败、超时、非 JSON、Schema 不匹配、目标不存在和世界能力校验失败。

- 世界保持冻结。
- 当前角色进入明确的决策错误状态。
- 已成功准备的其他角色结果保留。
- UI 显示可理解的错误摘要。
- 详细错误写入本地开发日志，敏感头和密钥必须脱敏。
- 玩家选择重试；重试创建新的 `requestId` 并关联原请求。
- 禁止自动生成一个假目标继续游戏。

### 18.2 插件与世界错误

- 插件加载、状态校验或效果校验失败时进入 `TECHNICALLY_BLOCKED`。
- 一个效果事务要么全部提交，要么完全不提交。
- 错误不能被 `catch` 后仅打印并继续返回成功。
- 恢复只能来自明确重试、重新加载正确插件或重新启动会话。

### 18.3 存储错误

关键 Event 或快照写入失败时，在下一个安全边界进入技术阻塞，保留内存世界并允许重试写入。不能继续产生无法恢复的新关键历史。

## 19. 测试策略

### 19.1 模拟单元测试

- 冻结状态下世界时间绝不增加。
- 固定世界步不受渲染帧率影响。
- 插件 Query 不能改变状态。
- EffectProposal 未经裁决不能进入世界。
- 同步竞争结果在相同输入下稳定一致。
- 随机状态可保存和恢复。

### 19.2 无界面场景测试

必须至少覆盖：

1. 未锁的门被程序自动打开，角色继续移动，不请求思考。
2. 已知路线遇到锁门，存在替代路线时自动绕行，不暂停。
3. 已知路线遇到锁门且无替代路线时，请求角色重新思考并冻结。
4. Bob 占用冰箱但 Alice 看不见时，Alice 不会凭空知道。
5. Alice 看见占用状态后形成目标冲突，才请求思考。
6. 角色内急越过紧急阈值后进入思考，选择并完成使用马桶，数值下降。
7. 一名角色重新思考时，其他角色动作进度完整保存并在放行后继续。
8. 模型响应期间无论现实等待多久，世界时间不变。
9. 过期模型响应被拒绝。
10. 模型失败显示错误，重试后继续；不存在静默兜底。

场景测试使用固定 `DecisionProvider`，不能依赖真实网络或模型随机性。

### 19.3 进程集成测试

- Local Server 与 Simulation Worker 的 Command/Event/Query 往返。
- Worker 崩溃和 IPC 断开转为技术阻塞。
- Event 与快照由 SQLite 单写者按序提交。
- WebSocket 断开重连后只能恢复只读显示，不创建第二个世界。

### 19.4 浏览器端到端测试

- 页面直接进入导演工作台，不显示营销首页。
- 地图、角色和素材实际渲染且画布非空。
- 思考状态、暂停原因、当前目标和感知内容可见。
- 决策审查开启时必须点击放行；关闭时自动继续。
- 错误状态提供重试操作。
- 在 `1280x720` 和一个较窄桌面视口检查文本不重叠、画布不空白。

## 20. 基础循环验收场景

实现完成时必须能够演示以下流程：

1. 启动项目后浏览器显示住宅、Alice 和 Bob。
2. 世界在 `T=0` 因两名角色初次思考而冻结。
3. 两个模型请求并发进行，界面仍能正常操作和查看状态。
4. 固定或真实模型分别给出结构化目标，世界时间仍为 `T=0`。
5. 审查开启时玩家放行，Alice 与 Bob 同时开始行动。
6. 程序完成路径规划、移动和未锁门自动开启。
7. Bob 先占用冰箱；Alice 在看不见时不会收到占用事实。
8. Alice 进入视野后看到 Bob 正在使用冰箱，当前目标产生冲突。
9. 程序确认没有唯一自动处理方案，Alice 请求重新思考，世界冻结。
10. Bob 和其他未受影响动作的进度完整保留。
11. Alice 的新模型决定经过校验后被放行，世界从同一时刻继续。
12. 内急紧急的角色能够决定使用马桶，程序完成执行并降低内急。
13. 整个过程中的重要结果、快照、模型采用结果和错误均可在本地追溯。

满足以上行为，才算基础循环完成。仅能显示地图、让角色移动或调用模型，不算完成。

## 21. 为延期功能保留的接口

首版不实现完整上帝工具，但所有世界修改已经只能通过 Command -> 校验 -> Event -> 提交的入口发生。以后玩家改变任何世界状态时复用同一入口。

首版不实现时间分支，但 Event、快照、世界版本和模型采用结果已经具备稳定因果标识。以后回滚和分支只扩展 `timeline` 与 UI，不改变模拟规则消息格式。

首版不实现社交，但 `HEAD` 槽位、感知事件和角色思考请求已经存在。以后聊天请求仍必须经过有限感知、模型决策和世界执行。

首版不实现地图编辑器，但地图已经是独立、版本化、可校验的 JSON。以后编辑器只成为该格式的可视化作者工具。
