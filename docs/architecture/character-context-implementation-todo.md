## 1. 已确认的行为约束

以下内容不是待选方案，实施时不得自行改写：

1. GodSimulation 自己持有角色上下文、日内对话、记忆和事件历史；模型供应商只接收由本地状态构造的单次请求。
2. `worldTick` 是唯一可写时间。天数、时刻、清醒时长和睡眠时长都从 Tick 与状态锚点派生，不增加第二套可写时钟。
3. 暂定时间比例为 `1 tick = 6 游戏秒`，即 `10 ticks = 1 游戏分钟`。世界创建后该比例不可修改；运行倍速只改变现实时间内推进的 Tick 数。当前 Worker 的 `100ms` 现实调度间隔不属于游戏时间语义。
4. 触发角色思考时进入世界级熔断。熔断期间 Tick、位置、需求、对象状态、任务及任务进度等模拟状态全部冻结；只有决策周期、请求结果和审查状态可以变化。
5. 外来感知只是给角色一次重新决策的机会，不自动改变或中断既有任务。角色可以继续原任务，也可以在新决策中替换任务。
6. 角色只有 `HEAD` 与 `BODY` 两条任务轨道；删除 `HANDS`，开门、拿取和使用物体等手部行为全部归入 `BODY`。
7. 每次模型决策必须同时输出 `head` 和 `body`。每条轨道只能选择 `continue` 或 `replace(taskOptionId, arguments)`；不提供独立的 `none`。无参数操作的 `arguments` 为空对象，所有参数都由对应操作的 Schema 校验。
8. 每条轨道都有标准空任务。清除任务等价于 `replace(emptyTask)`；空任务稳定存在，不会自然完成，也不会触发思考。
9. 任一非空任务自然完成后必须触发世界级熔断，让角色决定下一步；另一条尚未完成的轨道保持原任务和进度，可在决策中选择 `continue`。
10. `move` 完成后，在角色思考前将本次移动累计的 `nearby` 作为动作结果写入对话内容；`now` 不再由 `move` 特殊返回，而是在每次认知熔断时由系统统一提供最新视线信息。环境感知不放入系统提示词。
11. 稳定的长期记忆、长期目标、短期目标以及角色自己的衣物信息进入系统提示词；长期记忆位于上方，衣物信息紧随其后。
12. 上下文注意力预算暂以约 `200k tokens` 为目标。必要信息不为缩短而缩短，长期记忆需要压缩。
13. 疲惫压力由清醒时间压力与上下文 Token 压力加权叠加；当前暂定权重为时间 `0.6`、Token `0.4`，并另设独立技术硬上限。
14. 主动上床睡觉和压力过高导致的原地昏睡都会启动记忆整理。
15. 睡眠整理产生逐条的保留记忆与归档记忆；空间知识必须保持大致连续性。归档记忆跨天按时间和重要性衰减，低于阈值后删除，并通过 `recall` 工具检索。
16. 熔断时如何处理操作中间状态、是否产生回执以及回执包含什么，由该操作自己的生命周期协议规定。熔断回执不代表操作完成或取消，也不得改变冻结中的世界状态。
17. `move` 在熔断时按照自己的返回协议提供截至当前尚未返回的 `nearby`；当前 `now` 由认知熔断通道统一追加。炒菜操作在熔断时不返回任何炒菜结果，只有正常完成后才返回并生成物品。操作没有熔断回执不等于吞掉熔断原因，导致熔断的外来事件仍会进入角色对话。
18. 模型选择的每个任务对应一个语义操作。操作内部可以自动执行必要且确定性的微步骤，但程序不得自动串联下一个不同语义的操作；语义操作结束后按统一规则触发熔断。
19. 角色拥有总计 9 单位的物品携带容量，不使用固定格数或固定件数上限。每种物品声明自己的容量占用，角色携带物品的占用总和不得超过 9。
20. 携带物品与家具之间使用双向交互协议：物品声明自己可参与哪些家具交互，家具声明对应的处理方法；一次交互允许指定多个携带中的物品实例，并对整组输入原子处理。
21. 主动上床睡觉与疲惫压力过高导致的原地昏睡使用相同的逻辑唤醒规则：入睡时由 Tick 和待整理上下文规模确定 `wakeTick`；整理提前完成时只暂存结果，到 `wakeTick` 才原子提交并唤醒；到达 `wakeTick` 仍未完成时，世界级熔断停在该 Tick，待整理结果成功持久化后从同一 Tick 唤醒。模型 API 的现实耗时只能延长现实中的暂停，不能增加游戏内睡眠时间或改变模拟结果。
22. 任务既可以只占用 `HEAD` 或 `BODY`，也可以是同时占用两条轨道的一份同步任务。睡眠是一份 `HEAD/BODY` 同步任务，只有一个共享任务实例、进度和生命周期，不能只继续或只替换其中一半。
23. 每种任务可以声明结构化事件 `ignore` 规则；规则先按事件类别匹配，再按该事件 Schema 中的具体属性确定是否忽略，例如按角色实际接收到的声音音量过滤声音事件。命中忽略规则的事件不触发该角色的思考熔断；未被忽略的角色定向事件仍只提供决策机会，不自动改变任务。
24. 睡眠任务通过自己的事件 `ignore` 规则屏蔽不足以打扰睡眠的输入。未被忽略的事件触发统一熔断后，模型可以原子继续整份睡眠任务，或原子替换两条轨道而提前结束睡眠；只有替换睡眠任务时才作废未提交的整理结果。疲惫按实际睡眠 Tick 恢复，未完成整理时 Token 压力不下降，迟到的后台结果通过整理周期 ID 识别并丢弃。
25. 角色事件只有在匹配到的任务 `ignore` 规则完整覆盖 `HEAD` 与 `BODY` 两条轨道时才真正忽略。同步任务的一份匹配规则可以覆盖其占用的两条轨道；独立任务必须分别匹配并合并后覆盖两条轨道；空任务不提供忽略覆盖。任一轨道未被覆盖时仍触发统一熔断。
26. 时间疲惫恢复与上下文整理在睡眠中并行进行。逻辑睡眠时长使用 `max(minimumSleepTicks, timeRecoveryTicks, consolidationTicks)`，不得把时间恢复和 Token 整理时长相加；主动睡眠与强制昏睡使用同一语义。
27. 连续清醒 3 个游戏日对应 `43,200 ticks`。时间压力暂按该点归一化到 `1.0`；结合时间权重 `0.6`，组合疲惫的强制昏睡阈值暂定为 `0.6`，因此仅时间分量也会在连续约 3 天未睡时触发昏睡，Token 压力升高则可能提前触发；独立 Token 技术硬上限仍可直接强制昏睡。
28. 每次睡眠整理都以上一周期的保留记忆和本周期日内上下文为输入，重新产出下一周期的保留记忆与新增归档记忆。上一周期保留记忆没有自动续期资格；未被本次结果重新保留的内容必须被合并进其他保留条目或转入归档，不能静默继续进入下一周期系统提示词。
29. 记忆整理模型只负责为逐条记忆给出离散的语义重要性等级 `critical | high | normal | low`、判断理由和来源引用，不得直接输出任意浮点分数或删除时间。程序通过集中配置把等级映射为固定数值，并独占跨天衰减、阈值判断和实际删除；受保护的空间知识不进入普通归档衰减通道。
30. `recall` 与 `move` 属于同一套程序持有的语义操作工具协议，而不是决策周期内部的特权子流程。`recall` 是角色私有、只读且占用 `HEAD` 的有时长操作；其调用和最终结果通过通用工具消息协议自然保存在日内上下文中，并由后续睡眠整理统一处理。调用本身不得更新归档强度、重要性或衰减时钟。
31. 普通归档记忆使用按重要性等级配置半衰期的指数衰减：`strength = initialStrength * 2 ^ (-archiveAgeDays / halfLifeDays[importance])`。程序在跨日边界按归档年龄直接重算，低于统一阈值时删除；跨多日一次计算必须与逐日计算结果一致，不允许依赖连续浮点乘法累积。`critical` 仅表示半衰期最长，仍可最终遗忘；受保护空间知识不参与该公式。
32. `recall` 使用全文检索与向量语义检索共同生成候选，再按语义相似度、关键词匹配度和当前记忆强度加权排序。当前强度已经包含时间与重要性影响，排序不得再次单独加入时间分或重要性分。结果按程序控制的 Token 预算返回而不是固定条数；归档向量必须连同编码器 ID、版本、维度和模型文件身份一起持久化，禁止混用不兼容向量。
33. 角色可以连续执行多次 `recall`，但每次都是一个独立的 `HEAD` 操作：世界放行后 `BODY` 可同时继续，检索结果实际返回时所在的运行中 `worldTick` 就是该次回忆的完成 Tick，随后返回结果并按非空任务统一规则再次熔断。不存在固定回忆时长、按 Token 换算时长或“一次模型请求内部嵌套多次 recall”的特殊循环，也不设置专用的每决策调用次数上限；单次返回 Token 上限暂定 8,000，并继续受总上下文预算和疲惫机制约束。
34. 所有跨模块的模拟语义参数集中存放在版本化规则集 `content/rules/default.json` 中，并使用严格 Schema 校验；代码不得散落后备默认值。规则集随世界记录精确版本与内容哈希，恢复和回放必须使用相同规则。现实 Tick 调度、模型/API 地址、密钥和 GPU 设备等部署参数属于本地运行配置，不进入模拟规则集。
35. `recall` 的现实返回时刻是明确允许影响未来模拟时序的外部输入边界。系统必须持久化调用身份、开始 Tick、实际完成 Tick、编码器与索引锁及最终结果；历史恢复和回放消费该记录而不重新执行检索。由旧快照创建的新分支会重新检索，其后续时序允许因运行环境和负载不同而发生分歧。
36. 世界进入熔断并生成检查点后，本轮所有角色的决策输入立即封口。此后到达的异步结果按持久化接收序号排队，不得插入、撤回或重启已经发出的模型请求。若排队的是当前 `recall` 结果，本轮决策选择 `HEAD continue` 时在放行后于同一冻结 Tick 提交结果并再次熔断；选择 `HEAD replace` 时结果只保留审计记录，不进入角色上下文。
37. 记忆系统不进行语义去重、版本合并、晋升迁移或旧记录取代。睡眠整理产生的每条保留或归档记忆都按输出独立保存，即使内容与已有记忆重复；重复条目各自拥有形成与归档时间、重要性和衰减结果。检索时只合并全文与向量两路命中的同一数据库记录，不合并内容相似但 ID 不同的记忆。
38. 长期目标与短期目标只能由角色在正常决策中通过可选的结构化 `goalUpdates` 明确修改；睡眠记忆整理只有读取权，无权新增、改写、完成或删除目标。`goalUpdates` 与当次 `head/body` 任务选择在放行时原子提交；未提供更新时目标完整保持。任务完成不自动完成短期目标，目标变更必须由角色明确决定并进入自身日内上下文。
39. 长期空间知识是由睡眠整理维护的“区域语义地图”，不是坐标、路径格或逐次观察流水账。它按区域保存概略自然语言描述，内容包括区域间相对位置、区域用途、主要持久设施及其可提供的能力，例如“公寓左上是厨房，厨房内有冰箱可以存放物品，有锅可以炒东西”。未知区域不出现，门的当前开关、人物位置等短暂状态不写入长期空间知识。
40. 日内上下文明确区分主动操作链与自发感知链。`move`、`recall` 等角色主动选择的操作记录为带唯一 `callId` 的 `operation_call`，其正常、失败或协议允许的熔断回执记录为引用同一 `callId` 的 `operation_result`；声音、他人互动和其他非角色调用产生的输入记录为带认知事件身份及来源事件的 `perception_event`，不得伪造成没有对应调用的工具结果。两类消息按 Tick 与序号进入同一日内时间线，均不进入系统提示词。
41. 每次 operation 调用拥有独立 `callId`，operation 定义必须声明精确占用的任务槽位集合 `taskSlots`。普通并行的 `HEAD` 与 `BODY` 分别引用不同调用；任一调用先完成时只关闭自身并触发熔断，另一调用及其进度保持不变。多槽位 operation 是一份调用同时被声明的多个槽位引用，共享一个 `callId`、参数、进度和生命周期，不得复制为多份调用状态。
42. 多槽位 operation 必须原子进入和退出：进入时所有所需槽位必须在同一决策中选择同一候选及同一份规范化参数，并共同绑定一个新 `callId`；退出时所有槽位同时离开该共享调用，旧调用的取消生命周期只执行一次，随后允许 `HEAD` 与 `BODY` 各自启动不同的新调用。放行前必须预检完整的 `head/body/goalUpdates` 决策；任一候选、参数、槽位、目标补丁、取消或新调用前置条件失败时，整份决策拒绝且冻结检查点中的状态保持不变。
43. 未通过输出 Schema 或完整决策预检的模型响应只是无效决策尝试，不是角色实际作出的决定。系统保持同一冻结检查点与决策周期，以临时校验反馈要求模型重新输出完整的 `head/body/goalUpdates`；无效输出和纠错消息只进入模型调用与技术错误审计，不进入角色日内上下文或睡眠记忆整理。只有最终通过预检的完整决策才能写入角色上下文并放行；达到部署配置中的纠错尝试上限后进入 `TECHNICALLY_BLOCKED`，不得自动选择 `continue`、空任务或其他兜底行为。
44. Tick 是认知触发的唯一合并窗口。当前 Tick 第一个未被完整忽略的触发只设置 `freezePending`；引擎完成并提交该 Tick 的确定性管线后、推进下一 Tick 前统一生成检查点并熔断。每个受影响角色逐条保留该 Tick 内所有未忽略的任务生命周期信号与感知事件，不做语义合并或去重，并在同一个世界决策周期中各自发起一次思考。输入中先放当前调用的只读熔断回执，多槽位调用只生成一次，独立调用按 `HEAD`、`BODY` 稳定排序；随后按权威全局事件序号放入全部触发。检查点封口后到达的内容进入下一决策周期，不设置任何现实时间 debounce 窗口。
45. 沿用现有世界决策门控：同一决策周期内，所有被请求角色的有效决策只暂存，只有全部角色都 READY 后才允许放行；任何角色仍在等待、纠错或技术失败时世界继续冻结，其他角色已接受的决策也不得提前生效。放行时对整批角色决策做最终预检并以一次世界事务提交，失败则全部不生效。新 operation 在放行事务中只建立进度为零的调用状态，多个角色对同一世界资源的实际争用继续由恢复运行后的确定性 Tick 裁决，不能由模型返回顺序或角色遍历顺序决定。
46. operation 的世界效果与工具返回是两个独立通道。每个 `operation_call` 最终必须且只能产生一条引用同一 `callId` 的终态 `operation_result`，其结果信封明确标记 `completed | failed | cancelled`；业务载荷可以为空，但终态结果本身不能省略。世界熔断不结束调用，因此操作可以按协议产生 `terminal: false` 的中间回执，也可以不产生任何回执；`move` 返回截至熔断点的观察，炒菜保持无回执。终态结果只能描述实际成功提交后的世界状态与效果，不能声称未发生的产物或变化。
47. 已经在先前 Tick 提交的世界效果和事件都是不可回滚的事实。operation 被替换或失败时，尚未提交的完成效果直接丢弃；需要恢复占用、租约或其他状态时，由该 operation 的终止生命周期显式提交新的补偿效果和事件，而不是删除旧事实。旧调用退出、补偿效果、资源释放和终态结果必须原子完成；清理事务失败时保持冻结并进入技术失败处理，不能留下半清理状态。
48. operation 失败严格区分游戏内 `domain_failure` 与系统 `technical_failure`。只有顶层 operation 预先声明的稳定失败码及角色可见结果 Schema 才能关闭调用、生成 `failed` 终态结果、进入角色上下文并触发思考；无法由该 operation 自身局部恢复解决的正常争用、路径阻挡、材料不足等属于此类。内部微步骤的类型化受阻可以先由所属 operation 消费并尝试局部恢复，不等于顶层调用已经失败。插件异常、非法效果、Schema 错误、未知定义、状态不变量破坏以及任何未声明错误默认属于技术失败：调用保持未结束，世界进入 `TECHNICALLY_BLOCKED`，完整诊断只进技术审计，不进入角色经历或记忆。具有双重可能的底层错误只有经 operation 显式映射后才能转为游戏内失败，禁止按错误字符串猜测。
49. 衣服是具有唯一实例身份的物品，其定义保存不可变的样式语义锚点，实例保存当前整理、穿着等可变状态；程序持有实际穿着物品集合，模型负责依据这些事实维护详细的 `externallyVisible/internallyHidden` 外观描述。程序硬校验物品身份、归属、字段完整性和穿着集合，衣服主体样式与定义一致主要通过把样式锚点和当前状态完整提供给模型并施加强提示词约束，不能假装用普通字符串规则可靠判断语义一致性。
50. 不提供笼统的“换装” operation，只提供独立的 `wear`、`undress` 与 `adjust_clothing`：`wear` 使用角色随身携带的一件衣服实例并转入穿着态，`undress` 只指定当前穿着的一件衣服实例，不要求额外输入衣物，并在成功时将其转回随身物品集合；`adjust_clothing` 只改变衣服的整理/穿着状态与对应描述，不得改变其定义 ID 或主体样式。穿着中的衣服不占用随身携带容量；`undress` 候选不因当前剩余容量不足而消失，而是在 operation 首个执行步骤进行权威容量校验，容量不足时不改变任何物品或外观状态，返回已声明的“携带容量已满”游戏内失败结果并触发思考。每次成功操作都原子提交物品归属、穿着集合、衣服实例状态及该调用预先暂存的完整六字段外观快照，并返回新的外观结果。
51. 化妆是由梳妆台家具提供的专用 operation 候选，不作为角色在任意位置都能调用的通用操作。只有角色满足梳妆台的距离、占用和可用性条件时才提供候选；完成后通过同一外观状态事务更新模型维护的描述并返回结果。
52. 每个非空 operation 都必须通过公共执行时间接口为本次调用解析 `fixed(totalTicks)` 或 `indeterminate`。固定时长是调用建立时即可确定且锁定的正整数：调用在 Tick `T` 以进度零启动，正常且不中断时在 `T + totalTicks` 完成；固定时长不保证成功，首步校验或运行中的游戏内失败仍可提前结束。不确定时长不伪造预计完成 Tick，只在 operation 自身完成条件或异步结果实际就绪时结束。调用建立后时长类型及固定总 Tick 不得漂移；可能动态改道、无限等待或依赖外部返回而无法预知总时长的操作必须声明为不确定。空任务不是 operation 调用，不具有执行时间。
53. operation 的执行时间是对核心、模型上下文、检查器和回放都开放的结构化状态。调用持久化 `startedAtTick` 与时长类型，固定调用再保存 `totalTicks`；已运行游戏时间由当前 `worldTick - startedAtTick` 派生，熔断期间不会增长。不确定调用结束时持久化实际 `completedAtTick` 及完成来源，历史回放消费记录而不重新等待；由旧快照创建的新分支遵循已经确定的各类外部时序边界。固定时长参数来自世界锁定的规则或内容定义，不允许散落在业务代码中。
54. `wear`、`undress`、`adjust_clothing` 与化妆的初始 `operation_call` 参数必须包含模型在本次决策中生成的完整六字段 `appearanceAfter`；完成时不得再发起一次隐藏模型调用。核心将该快照随 `callId` 作为待提交数据持久化，调用建立和执行期间都不改变权威外观。熔断后选择 `continue` 时保留它，选择 `replace`、首步游戏内失败、运行中失败或取消时随旧调用一起丢弃；正常完成时重新校验当前权威前置条件与快照 Schema，并和物品归属、穿着集合、衣服实例状态原子提交。执行期间其他角色仍看到旧外观以及“正在穿衣/脱衣/整理/化妆”的当前行为，只有成功完成后才看到新外观。
55. 角色的稳定身体事实由程序以独立、结构化的 `bodyFacts` 持有，至少可以表达已声明的发色、基础发型、体型、身体特征和永久标记；未声明的事实保持未知，不得从外观文字反向猜测。六字段外观只是基于 `bodyFacts`、衣服样式锚点、衣服实例状态与当前操作生成的模型撰写投影，不能成为身体事实的唯一来源，也不能反向覆盖 `bodyFacts`。每次生成 `appearanceAfter` 都必须同时提供完整 `bodyFacts`、当前穿着物品及样式锚点、实例状态、旧外观和本次预期变化。只有协议明确声明可提交 `bodyFacts` 变更的 operation 或 effect 才能修改它；普通穿衣、脱衣、整理衣服和化妆没有该权限。
56. `move` 是占用 `BODY` 的 `indeterminate` operation，其完成时刻不能由初始路径长度固定推算。首次寻路时，具有自动通行能力的门不视为障碍；角色到达门前后由同一个 `move` 调用执行自动开门微步骤。开门成功则继续原移动；因门锁住等已声明原因失败时，先把该门作为带对象版本和来源事件的已知阻挡，再从当前位置为同一目的地重新寻路。存在替代路线时不熔断、不结束或更换 `callId`，直接继续移动；没有替代路线时才以游戏内失败结束 `move`，返回锁门原因及截至当前位置的 `nearby` 并触发思考。移动视觉累积由实际经过的完整轨迹与视线扫掠驱动，与一次 Tick 移动多少格、Tick 调度和渲染帧无关；凡实际扫过且可见的内容都进入概略 `nearby`，重复内容略去。
57. 视觉系统严格区分连续视觉状态与认知视觉事件。位置、距离、方向和操作进度等连续变化只更新角色当前视觉状态，不触发熔断；只有其他角色从不可见变为可见、可见角色的公开行为发生语义变化，或可见角色的对外外观在成功事务后变化，才分别生成 `character_appeared`、`visible_behavior_changed` 或 `visible_appearance_changed`。角色从可见变为不可见只更新当前视觉状态，不生成认知事件，也不熔断。同一可见阶段内位置持续变化不得重复生成“出现”事件；认知事件仍经双轨任务 `ignore` 规则过滤，同 Tick 多个事件只触发一次世界熔断。不增加事件等级、冷却时间或模型相关性判断。
58. 每次真正请求角色思考的认知熔断都必须从已封口的冻结检查点为该角色生成一份最新私有 `perception_now`，作为日内对话内容追加在本轮操作回执和触发事件之后。它使用相对方位而非坐标，包含当前可见类别、可见角色的公开行为与 `externallyVisible` 外观、可见对象状态及当前可选操作；它没有 `callId`，不是新的感知事件，也不会再次触发熔断。`move` 只返回沿途累计的 `nearby`，不再拥有特殊的 `now` 返回职责。技术阻塞若没有发起角色思考，则不伪造 `perception_now`。
59. 每个 operation 定义都必须显式声明 `publicBehavior`：只能声明 `hidden`，或提供不含私有数据的结构化观察者可见投影；不存在省略后的默认值，也不允许引擎根据 operation ID、参数或内部阶段自行猜测。`move`、如厕、穿衣和脱衣等投影其公开动作；`speak` 的视觉投影只表达“正在说话”，具体内容进入听觉；`recall` 最多表达一般性的“正在思考”，不得泄漏查询或结果。投影不得包含 `callId`、私有参数、私有目标或插件内部状态。并行 `HEAD/BODY` 调用按稳定槽位顺序组合，多槽位调用只投影一次；`visible_behavior_changed` 只比较组合后的公开语义投影，不比较内部任务身份、逐 Tick 进度或私有阶段。
60. 家具和其他世界物体的定义必须基于其结构化公开观察投影，显式声明一组可以为空的认知触发状态边沿。只有公开状态事务已经提交、对象在该观察者当时的视野内且前后状态匹配已声明边沿时，才为该观察者生成 `visible_object_state_changed`；例如可以声明“开始起火”，而普通时钟进度或连续数值变化可以不声明。未声明的公开变化只更新连续视觉状态并在下一份 `perception_now` 中体现，私有状态永不参与匹配或载荷。不按任意字段变化自动熔断，也不增加事件等级、冷却时间或 LLM 相关性判断。
61. operation 可以声明自己必须指定一个作用角色；这类调用的参数必须包含经过候选与权威前置条件校验的 `targetCharacterId`，并在调用建立后随 `callId` 锁定和持久化。该 operation 按自身协议产生角色互动事件时，事件只写入这个目标角色的私有事件队列并只请求该角色思考，不向所有角色广播；发起者从自己的 operation 回执获知结果，旁观者只能通过各自实际获得的视觉或听觉输入得知。`speak` 明确不属于此类，其参数不指定作用角色：它只产生声音，信息通过环境传播，实际接收角色完全由听觉系统决定。
62. 需要指定作用角色的 operation 一律在正常执行完成并成功提交实际效果后，才向目标角色发送互动事件；调用开始、执行中、熔断中间态、失败或取消都不通过这条定向通道提前通知。实际效果、发起者的成功终态回执和目标角色的互动事件必须在同一个原子事务中提交，随后按正常 Tick 管线触发熔断；事务失败则三者都不生效。目标角色仍可能在此前通过视觉或听觉独立察觉公开行为或声音，这不属于定向互动通知。
63. 目标角色收到的互动事件是否写明发起者身份，只取决于 operation 完成并提交效果后的同一 Tick 中，目标角色能否实际看见发起者。能看见时可以写明公开姓名；看不见时只能写“有人”及目标实际受到的作用，不得在角色可见载荷、正文或适配器隐藏字段中泄漏发起者 ID 或姓名。程序内部的权威效果事件和审计记录仍保存真实发起者 ID，用于恢复、回放和调查，但不得直接作为模型可见事件序列化。
64. 时间属于角色当前感知。每次真正请求角色思考时，`perception_now` 必须包含由冻结检查点 `worldTick` 通过唯一时间投影 API 得到的当前游戏日与时分，不向模型暴露原始 Tick。时间自然流逝本身不生成感知事件或触发熔断；角色只在因其他原因开始思考时获得当时的最新时间。
65. 每条实际投递的声音事件都必须标注权威声源。角色发声时标明发声角色，即使接收者当前看不见对方，也可依据音色得到该来源；家具、物体和环境声音标明对应对象或环境来源。声源由程序根据产生声音的权威实体确定，不能由模型填写，也不携带 operation 私有参数或 `callId`。完整听见和距离较远的模糊内容都保留声源标注；完全听不见时不投递任何声音事件或声源信息。
66. 每条实际投递的声音事件还必须包含相对于接收角色当时朝向的大致方位，例如前方、左侧或右后方；方位由声音送达 Tick 的权威声源位置、接收者位置和朝向确定，同一持续声音后续再次产生事件时重新计算。角色可见内容不得包含声源或接收者的世界坐标，距离模糊只影响声音内容，不删除已经计算出的来源与相对方位。
67. 当前声音系统首先服务于 `speak`。一次 `speak` 正常说完后只产生一个瞬时声音事件，在完成 Tick 一次性确定实际听见者，并向他们分别投递完整或模糊的说话内容、声源和相对方位，随后让这些角色思考；同 Tick 多名听者仍只形成一个世界熔断批次。该次说话不建立持续声源，也不额外产生声音开始或声音消失事件；`speak` 失败或取消时不投递尚未说完的内容。
68. 持续声音作为后续环境音能力处理。对每个角色，持续声源从听不见变为听得见时产生声音出现事件，从听得见变为听不见时产生声音消失事件，声源产生新内容时按当时状态投递内容事件；仍处于可听范围内时，仅方向、距离或接收音量连续变化不产生事件或熔断，只更新听觉状态，下一次内容事件使用最新的来源、方位和接收强度。
69. `speak` 的发声音量只能从“小声、正常、大声”三档中选择，不接受任意数值。每档对应的声源初始强度由世界锁定的版本化规则集配置；清晰听见、模糊听见和完全听不见的实际边界继续由该强度、统一声音衰减和接收阈值派生。模型只选择三档，不能直接控制底层强度或传播距离。
70. 物品容量占用一律为**非负整数**（抽象体积单位），不允许小数或浮点，避免累加顺序破坏同输入必同结果。堆叠物品只声明单件占用，整组占用由世界按 `单件占用 × 数量` 计算，插件不得为堆叠态另行声明一个占用值。占用数值不持久化到物品实例，读取时按当前规则集现算；规则集本身版本化，历史回放使用当时的版本，因此容量变更不需要迁移脚本，也不存在快照值与规则集不一致的中间态。
71. **不支持容器嵌套**：只有角色与家具可以持有物品，物品不能容纳其他物品，容量计算因此不递归。
72. 物品在世界中的形态与转移：抛弃后的物品是带世界坐标的**独立实体**，参与现有的 FOV/LOS 计算，不作为某个房间级容器内的抽象条目；落点固定为抛弃时角色当前所在格，不按朝向推导，也不做兜底格查找。销毁不是通用能力，由物品插件在自己的 `interactions` 中可选声明，核心不注册可在任意对象上调用的通用销毁操作。角色之间的物品转移采用**两步协议**：发起方的 `give` 在正常完成时才写入「待转移」状态并让目标角色感知，目标角色必须自己决策执行 `accept` 才完成归属转移；引擎不得在 `give` 完成时自动转移归属，也不得要求目标角色在 `give` 开始或执行期间响应。
73. **说明书机制**：核心提供通用 `read` 工具，系统提示词声明其存在，角色按需调用。`read` 以对象**类型**（定义 ID）而非实例为输入，返回该对象插件在定义中声明的静态使用说明。说明书只描述「这个对象支持哪些操作、各自需要什么输入与前置条件」，不包含当前可用状态——可用性一律由对应 operation 的 `canStart` 依据权威状态实时判定，因此说明书不会因世界波动而过期，也无需记录「角色读过哪些实例」。这与 skill 的渐进式披露同构：用法不预先注入上下文，需要时才读。
74. **不存在复合 operation**，前置条件由角色逐个满足。一个语义操作不得在其内部静默串联其他语义操作：例如「做菜」不会自动完成「放蛋」「放番茄」，后者是物品各自声明的独立 `put_into` 操作，由角色分次决策执行，每次结束后触发熔断。**这不排斥单个语义操作接受多个物品实例作为输入**——阶段 12 第 403、406 条明确支持一次指定多个物品并原子处理；本条禁止的是跨越语义边界的自动串联。消耗型操作的产物规则（配方）写在版本化内容定义中，插件只负责按当前权威状态查表并生成对应产物；产物必须先是真实的世界效果（生成物品实例），再作为 `result` 告知模型，不能只返回一段描述性文本。
75. **候选生成不过滤前置条件**。候选按可达性与目标类型生成，核心不在候选阶段调用 `canStart` 预筛，操作的前置条件与用法由角色通过 `read` 说明书理解。角色选中前置不满足的操作时，operation 在首个执行步骤以权威状态校验，不满足则以已声明的游戏内失败码原子关闭调用、说明缺失原因并触发思考，保持所有状态不变。这条与第 50 条「`undress` 候选不因剩余容量不足而预先隐藏」是同一条原则。
76. **一切物品行为由 operation 声明**。物品插件只声明能力（`capabilities` / `movement` / `vision` / `traversal` / `occupancy` / 说明书）与 `interactions` 列表，不存在 `equippable`、`visible`、`destroyable`、`droppable` 这类类别字段；装备是 operation 而非物品属性，掉落与销毁由角色执行对应 operation 时的状态决定。所有游戏内操控——移动、说话、使用家具、使用物品、`recall`——都是同一个 `OperationContract` 的实现，共享同一套生命周期、失败码目录与终态协议。
77. **operation 的目标需求与能力体系**。operation 一律定义在宿主对象（物品或家具）的 `interactions` 内，不存在脱离宿主独立存在的 operation：宿主自身的 operation（如锅的 `cook`）其目标隐含为宿主实例本身，由候选生成时绑定的宿主确定；只有作用于外部对象的 operation（如鸡蛋的 `put_into`）才需要声明目标需求——目标角色，或写明 `requiredCapabilities` 的目标对象。核心用它做三件事——候选生成时按能力过滤（附近没有具备该能力的对象时该 operation 不进候选）、调用建立时校验模型填入的实例确实具备该能力、并把目标 ID 随 `callId` 锁定进事件与快照。对象定义在 `ObjectDefinition` 上以 `capabilities: string[]` 声明自己具备的能力（如 `["cooling", "storage"]`），与 `tags` 严格分离：`tags` 只表达类别（如 `home` / `food`），`capabilities` 只表达能力（如 `heating` / `cooling`）。领域能力数量无限、无法穷举成固定字段，故用字符串列表；空间类能力继续沿用 `movement` / `vision` / `traversal` / `occupancy` 结构化字段。能力用于匹配，类别不用于匹配——这是「只认能力，不认类别」在操作目标层的落实。
78. **声音传播受遮挡影响**：墙与门都会衰减声音，衰减系数写入规则集；静态墙的遮挡可预计算，动态门在传播时实时叠加。**不考虑区域环境噪声**——不为区域设置背景噪声基线，听清程度只由声源强度、传播衰减（含墙门遮挡）与接收阈值派生。本条扩展约束 69 的「统一声音衰减」，不是替换它。

## 2. 可复用的现有基础

以下能力已经存在，后续工作应扩展它们，不重新建立平行实现：

- 独立模拟进程持有唯一权威世界状态。
- `RUNNING`、`THINKING`、`READY_FOR_RELEASE`、`TECHNICALLY_BLOCKED` 世界模式与冻结流程。
- 冻结期间 Tick 和既有动作进度不变化的场景测试。
- 确定性 Tick 管线、领域事件、原子检查点、恢复和模型调用审计。
- FOV、LOS、空间索引和角色主观知识隔离。
- 动作规划、进度推进和对象交互占用槽的初版实现。
- SQLite 事件、快照、模型调用和技术错误存储。

当前运行时已迁移为 `HEAD/BODY` 双轨、`activeOperations` 与完整 `TaskDecision`；`currentGoal/actionPlan/bodySlots`、`goalOptionId` 和 `HANDS` 只保留在旧快照及旧数据库记录的迁移边界中。当前批次完成的是可恢复的 operation 基础，通用操作回执、事件 ignore 的运行时判定、`goalUpdates`、`speak`、`recall`、衣物与物品仍按下列阶段继续实现。

- [ ] 补齐替换执行中对象交互时的取消、占用释放和失败回执规则，禁止遗留对象锁或重复提交效果。
- [ ] 任一非空任务成功、发生顶层已声明的游戏内失败或客观上无法继续时触发决策熔断；被 operation 自身成功局部恢复的内部受阻不触发熔断，另一条轨道保持不变。技术失败直接进入 `TECHNICALLY_BLOCKED`，不得伪造成角色认知触发。
- [x] 任一同步任务完成、失败或被替换时只执行一次生命周期处理，并原子释放两条轨道；被双轨替换时旧调用的取消生命周期也只执行一次，不得重复提交效果、回执或整理事务。
- [ ] 将 active operation 的 `startedAtTick`、时长类型、固定 `totalTicks`、实际终止 Tick 与终止来源纳入领域事件、快照、恢复和分支；恢复固定调用时沿用原锁定值，不重新执行 `resolveDuration`，历史回放不重新等待不确定调用的已记录完成信号。
- [x] 为两个独立调用建立完成顺序测试：先完成者只生成自己的结果并触发熔断，未完成调用的 `callId`、参数、进度和占用全部不变，模型可对其选择 `continue`。
- [ ] 建立操作协议契约测试：固定调用在精确 Tick 完成且熔断现实耗时不计入进度，不确定调用只响应明确完成信号，恢复不会重算锁定时长；`move` 在初始路径变化、自动开门、锁门后绕行和无路可走时始终遵守同一不确定时长调用，熔断时产生非终态回执但进度不变；产出型测试操作熔断时无回执且不提交完成效果；正常完成、执行失败和被替换分别只关闭一次 `callId`，补偿失败不会留下半清理状态；真实物品生成留到阶段 12 接入。
- [ ] 明确 operation 一律定义在宿主对象（物品或家具）的 `interactions` 内，不存在脱离宿主独立存在的 operation；宿主自身的 operation 其目标隐含为宿主实例本身。在 operation 契约层增加统一的目标需求声明：无目标、目标角色，或写明 `requiredCapabilities` 的目标对象（如鸡蛋的 `put_into` 需要 `["heating"]`）。核心据此完成三件事——候选生成时按能力过滤、调用建立时校验模型填入的实例确实具备该能力、把目标 ID 随 `callId` 锁定进事件与快照。禁止各 operation 自行约定目标字段名，否则核心无法统一校验与锁定。
- [ ] 候选生成**只按可达性与目标能力过滤，不调用 `canStart` 预筛前置条件**：操作的前置条件与用法由角色通过 `read` 说明书理解。角色选中前置不满足的操作时，由 operation 在首个执行步骤以权威状态校验，不满足则以已声明的游戏内失败码原子关闭调用、说明缺失原因并触发思考，保持所有状态不变。与阶段 3「`undress` 候选不因剩余容量不足而预先隐藏」是同一条原则。
- [ ] 建立 operation 契约测试：所有注册的操作——移动、说话、物品交互、`recall`——都通过同一份 `assertOperationContract` 校验，共享生命周期与终态流程；拒绝缺少 `taskSlots` / `parametersSchema` / `eventIgnore` / `publicBehavior` / `domainFailures` / `resultSchema` 中任一项，或自行发明终态流程、绕过 `terminal` 标记的 operation。
- [x] 更新模型网关的结构化输出 Schema、提示词响应格式、固定测试模型和决策审查界面。

**完成门槛：** `HEAD` 与 `BODY` 能并行推进；任一轨道完成后世界冻结；模型可继续其中一条并替换另一条，继续的轨道没有任何进度损失；不同操作能在同一次熔断中按各自协议返回不同的中间态内容；需要目标的操作在附近没有具备对应能力的对象时不进入候选，填入不具备该能力的目标时在调用建立阶段被拒绝。

### 阶段 2：Tick 派生时间基础

- [x] 在世界规则锁中持久化不可变的 Tick 时间比例 `secondsPerGameTick = 6`，并统一派生 `ticksPerGameMinute = 10`；Worker 的现实调度间隔不进入规则锁。
- [x] 明确并持久化世界纪元：默认规则的 Tick 0 为第 1 天 08:00，使 `worldTick` 可以确定性派生游戏日、时、分和跨天边界。
- [x] 提供唯一的时间投影 API `projectGameTime`、`ticksPerGameMinute` 与 `ticksPerGameDay`，当前界面与模拟投影不再各自计算日期时刻。
- [ ] 提供面向角色的时间感知投影，把冻结检查点的 `worldTick` 渲染为当前游戏日与时分并写入每份 `perception_now`；不得暴露原始 Tick，也不得因分钟、小时或日期自然变化单独产生感知事件。
- [ ] 为角色记录必要的 Tick 锚点，例如最后醒来、入睡和记忆整理开始的 Tick；时长本身不作为第二份可写状态保存。
- [ ] 保证世界倍速只影响 Tick 调度频率，不改变同一 Tick 对应的游戏时间。
- [x] V3 快照通过规则锁与 `worldTick` 保存时间投影所需的唯一输入；恢复、SQLite 持久化、历史审计、界面显示以及冻结/分钟/跨日边界已有测试覆盖，派生值本身不重复写入状态。

**完成门槛：** 相同的世界配置与 Tick 在运行、恢复和回放中始终得到相同日期与时刻；冻结期间所有派生时间不变化。

### 阶段 3：最小可穿戴物品内核与角色外观状态

- [ ] 从后置物品系统前移不可再拆的最小内核：稳定的物品定义 ID、唯一物品实例 ID、容量占用、角色随身物品集合，以及至少 `carried | worn` 的互斥归属状态；后续完整物品系统只能扩展这套身份和归属，不能另建衣物专用伪物品。
- [ ] 为角色定义独立、结构化且带 Schema 版本的权威 `bodyFacts`，保存已声明的稳定身体事实；缺失字段表示未知，禁止从六字段外观描述、衣物描述或模型常识反向补全。
- [ ] 在 operation/effect 协议中增加显式的 `bodyFacts` 写权限与结构化变更载荷；未声明该权限的效果一律不得修改身体事实，穿衣、脱衣、整理衣服和化妆均不声明该权限。
- [ ] 为衣服物品定义不可变的样式语义锚点，为衣服实例定义可变的整理/穿着状态；任何外观文字变化都不得改写衣服定义 ID、实例 ID 或样式锚点。
- [ ] 定义角色自行持有的结构化衣物状态，固定包含 `externallyVisible` 与 `internallyHidden`。
- [ ] 两个可见性分区都固定包含头部、上身、下身字段；没有内容时明确写“无”，不得臆断未声明衣物或身体信息。
- [ ] 在权威外观状态中同时保存实际 `wornItemIds` 与模型撰写的完整六字段描述；程序校验描述快照引用的穿着集合与真实物品归属一致，但不使用关键词匹配冒充样式语义校验。
- [ ] 在角色生成 operation 决策时提供完整 `bodyFacts`、当前穿着物品及不可变样式锚点、衣服实例状态、旧外观和该候选的预期状态变更；`wear`、`undress`、`adjust_clothing` 与化妆的调用参数 Schema 都要求模型同时给出完整六字段 `appearanceAfter`，不得等到完成时再调用隐藏模型补写。
- [ ] 将规范化后的 `appearanceAfter` 绑定 `callId` 作为待提交数据持久化；调用开始和执行中的中间效果都不得提前改写权威外观，保存、恢复和回放必须保留同一份候选快照。
- [ ] 支持赤裸状态：外见字段描述实际可见身体，内见字段全部为“无”。
- [ ] 提供只读的对外外观接口；其他角色的感知系统只能读取 `externallyVisible`。
- [ ] 角色自身上下文可以读取两个分区，其他角色、网页投影和插件按权限分别测试，防止私有信息泄漏。
- [ ] 不注册通用“换装” operation；分别注册使用一个随身衣服实例的 `wear`、只指定一个当前穿着实例的 `undress`，以及只修改实例整理/穿着状态的 `adjust_clothing`。这些物理操作归入 `BODY`，并遵守通用 operation 生命周期和终态返回协议。
- [ ] 穿着中的衣服不计入 9 单位随身携带容量；`wear` 成功时从 `carried` 转为 `worn` 并释放对应容量，`undress` 成功时从 `worn` 转为 `carried` 并重新占用容量。
- [ ] 只要目标衣服当前确实处于穿着态就可提供 `undress` 候选，不用剩余容量预先隐藏候选。operation 在首个执行步骤以权威状态校验容量；容量不足时以已声明 `carry_capacity_full` 游戏内失败原子关闭调用，返回“携带容量已满”，保持物品归属、外观和容量完全不变并触发思考。
- [ ] `adjust_clothing` 的参数和结果必须保持同一衣服实例与定义样式锚点，只允许改变褶皱、开合、位置、整齐程度等实例状态及相应外观描述。
- [ ] 由梳妆台家具提供化妆 operation 候选；角色不在可交互位置、家具被占用或不可用时不提供该候选，核心不注册可在任意地点调用的通用化妆操作。
- [ ] `wear`、`undress`、`adjust_clothing` 和化妆正常完成时，依据当时的权威状态重新校验操作前置条件、物品身份与归属、穿着转换、实例状态及 `appearanceAfter` Schema；全部通过后原子提交相应状态与该调用暂存的完整外观快照，再生成工具结果和领域事件。
- [ ] 首步游戏内失败、运行中失败或取消时丢弃待提交的 `appearanceAfter`，不得改变权威外观；熔断后的双轨决策选择 `continue` 时保留同一份快照，选择 `replace` 时随旧调用取消而丢弃。
- [ ] 在 operation 执行期间，对自身和观察者继续投影旧的权威外观，同时独立显示“正在穿衣/脱衣/整理衣服/化妆”的当前行为；只有正常完成事务提交后才投影新外观。
- [ ] 将 `bodyFacts`、最小物品内核、穿着状态、模型外观快照及变更事件纳入快照、恢复和回放；恢复后不得依赖重新解析旧外观来重建身体事实。
- [ ] 物品容量占用一律为**非负整数**，不得使用小数或浮点；堆叠物品只声明单件占用，整组占用由世界按 `单件占用 × 数量` 计算，插件不得为堆叠态另行声明占用值。占用数值不持久化到物品实例，读取时按当前规则集现算，因此容量变更不需要迁移脚本。
- [ ] 在 `ObjectDefinition` 上新增 `capabilities: string[]` 字段，与 `tags` 严格分离：`tags` 只表达类别（如 `home` / `food`），`capabilities` 只表达能力（如 `heating` / `cooling` / `storage`）。同步更新插件 SDK 的类型校验与现有插件定义，并建立测试确认两类字段不混用。
- [ ] 实现**说明书机制**：核心提供通用 `read` 工具并在系统提示词中声明其存在，角色按需调用；`read` 以对象类型（定义 ID）而非实例为输入，返回插件在定义中声明的静态使用说明。说明书只描述该对象支持哪些操作及各自所需输入与前置条件，**不包含当前可用状态**，可用性一律由 `canStart` 依据权威状态实时判定。对缺少说明书声明的对象定义建立加载期拒绝。
- [ ] 建立测试：容量占用恒为整数且整组等于单件×数量；规则集调整后读取结果随之变化且无需迁移；同一类型的不同实例返回同一份说明书；说明书内容不随世界状态漂移；`read` 不泄漏未声明的私有状态。
- [ ] 建立提示词与场景测试，覆盖穿衣、逐件脱衣、满容量脱衣失败、失败后状态不变、整理同一件衣服、赤裸、梳妆台可用性、样式锚点保留、模型漏字段、物品归属错误、执行中仍显示旧外观、熔断后继续保留候选、替换后丢弃候选、反复穿脱后身体事实不漂移、无权限效果不能修改 `bodyFacts`、未知身体事实不被臆断以及私有描述隔离。

**完成门槛：** 身体事实、衣服实例及主体样式始终可追溯，角色只能通过穿衣、脱衣、整理衣服或梳妆台化妆改变完整外观；这些外观操作不会改写身体事实，自身能看到两个分区，观察者只能得到外见字段，保存恢复后身体事实、物品归属与描述仍一致。

### 阶段 4：视觉感知结果与动作回执

- [ ] 在现有 FOV/LOS 之上分别定义结构化 `nearby` 与 `perception_now` 协议，先保存结构化事实，再由认知层渲染自然语言；前者属于 `move` 调用，后者属于通用认知熔断输入。
- [ ] 让移动执行器按实际发生顺序输出完整轨迹与朝向变化，视觉累积器消费轨迹上视线扫过区域的并集；该接口不能依赖“每 Tick 最多移动一格”的假设，即使一个 Tick 跨越多格也必须覆盖所有中间轨迹，不能因 Tick 调度、世界倍速或渲染抽帧漏掉实际扫过的内容。
- [ ] 把整个 `move` 期间扫过的信息聚合到该调用的结构化 `nearby`；按类别与实体略去重复内容，再渲染为简短概括，不把每次采样、每个坐标或逐 Tick 观察写成流水账。
- [ ] `nearby` 保持概略描述，并记录实际看见的其他角色行为及其对外可见衣物。
- [ ] `move` 成功后生成只包含本次尚未返回之沿途累计 `nearby` 的动作结果，随后按非空 operation 的统一规则触发思考；终点当前视线由本轮通用 `perception_now` 提供。
- [ ] `move` 因其他事件触发熔断时，调用自己的熔断处理并返回截至冻结位置尚未返回的 `nearby`；该回执不结束移动任务，当前视线仍由通用 `perception_now` 提供，选择 `continue` 后从原进度继续。
- [ ] 由 `move` 操作定义多次熔断之间的视觉累计与去重游标，保证已经返回的观察不会丢失，也不会在后续回执中无意义重复。
- [ ] `move` 失败时返回截至失败点尚未返回的 `nearby` 和可感知的失败原因，当前位置视线由通用 `perception_now` 提供，随后触发思考。
- [ ] 自动开门成功和锁门后存在替代路线都作为 `move` 内部局部恢复继续执行；实际感知到的开门、受阻与改道事实保留在该调用的结构化累计结果和事件审计中，但只有无替代路径导致顶层 `move` 失败时才触发思考。
- [ ] 为单 Tick 跨多格、弯道转向、方向措辞、稳定排序、重复内容略去、遮挡变化、自动开门、锁门后绕行、锁门且无路以及不可见私有衣物建立确定性测试。

**完成门槛：** `move` 无论初始路径长度、单 Tick 位移和途中自动改道都保持同一个不确定时长调用；正常完成、无路失败和中途熔断均能提供正确的沿途 `nearby`，角色同时从通用认知输入获得冻结位置的最新 `perception_now`，两者都没有坐标流水账、重复灌入和全知信息。

### 阶段 5：角色定向事件与世界级思考熔断

- [ ] 定义角色定向的 `perception_event` 信封，至少包含世界、目标角色、Tick、事件序号、认知事件 ID、来源事件和结构化载荷；它不携带操作 `callId`。
- [ ] 区分“模拟事实事件”“投递给角色的感知内容”和“触发思考的信号”，避免事件一产生就向所有角色广播。
- [ ] 将每 Tick/移动子步产生的连续视觉快照与认知视觉事件分开：当前可见集合、相对方位、距离和位置可以持续更新，但不得把任意坐标变化或操作进度变化直接接入熔断触发器。
- [ ] 从 active operation 的 `publicBehavior` 生成角色当前公开行为：`move`、如厕、穿衣和脱衣等输出对应公开动作；`speak` 的视觉投影只表示正在说话，话语内容只走听觉；`recall` 只能投影为一般性的正在思考，查询、结果、`callId`、私有参数、私有目标和插件内部状态不得进入观察者视图。
- [ ] 同时存在独立 `HEAD/BODY` 调用时按 `HEAD`、`BODY` 稳定顺序组合非隐藏投影；同一个多槽位 `callId` 只投影一次。组合结果必须纳入快照和回放，不能因容器遍历顺序产生不同文本或版本。
- [ ] 扩展家具和世界物体的观察定义，使其基于自身公开状态 Schema 显式注册可为空的认知触发边沿目录；每条边沿使用稳定 ID 和受限、类型安全的前后状态条件，定义加载时拒绝缺失声明、引用私有字段或执行任意脚本。
- [ ] 只在对象公开状态事务提交后，对当时能看见该对象的观察者匹配认知触发边沿并生成 `visible_object_state_changed`；载荷只包含对象公开身份/类别、相对方位、边沿 ID 和该边沿明确开放的公开变化。未声明的变化只刷新连续视觉状态及后续 `perception_now`。
- [ ] 基于前后两个已提交视觉状态检测人物语义边沿，只为 `不可见 -> 可见`、可见人物公开行为语义变化和可见人物对外外观版本变化生成 `character_appeared`、`visible_behavior_changed`、`visible_appearance_changed`；`可见 -> 不可见` 不生成事件。
- [ ] `character_appeared` 载荷包含观察者实际看见的相对方位、角色当前公开行为和 `externallyVisible` 外观；`visible_behavior_changed` 只比较规范化后的组合公开投影，不比较 operation ID、内部任务、逐 Tick 进度或私有阶段，外观变化只在外观事务成功提交后产生。
- [ ] 为每名观察者持久化人物的当前可见阶段与最后已投递公开版本；同一阶段内持续移动不能重复触发“出现”，离开视野只关闭该阶段，之后重新进入才建立新的出现事件。快照恢复与回放必须产生相同边沿。
- [ ] 建立按角色分发的事件路由。需要指定作用角色的 operation 正常完成后，只以该调用已经锁定的 `targetCharacterId` 作为互动事件接收者并写入其私有事件队列；发起者依靠自己的 operation 回执，旁观者依靠视觉或听觉，三条输入不得互相冒充或重复投递。
- [ ] 在完成事务拟提交的效果状态上计算目标角色对发起者的最终可见性，再生成目标可见的互动事件：可见时写明公开姓名，不可见时使用匿名描述且不携带发起者 ID 或姓名。内部权威事件保留真实发起者 ID，但模型消息渲染器只能读取经过该次可见性裁剪的载荷。
- [ ] `speak` 只产生声音输入，参数中不指定作用角色，也不使用 operation 的作用角色定向投递；说话内容由听觉系统按“小声、正常、大声”三档之一、距离和后续遮挡规则分别投递给实际听见的角色，不接受模型直接填写底层强度或传播距离。
- [ ] 将 `speak` 的听觉效果定义为正常完成时产生的一次瞬时声音：在完成 Tick 计算全部实际听者并分别生成一条角色私有声音事件，不建立持续声源或额外的开始/消失事件；失败和取消不投递完整说话内容。
- [ ] 在阶段 5 的声音事件载荷中预留必填声源和相对方位字段：角色声源引用实际发声角色，家具、物体和环境声源引用实际对象或稳定环境来源；方位以接收者在该事件 Tick 的朝向表示为前后左右等大致方向。接收者看不见声源不影响这两个字段，范围外未收到声音的角色也不得获得声源或方位信息。
- [ ] 扩展任务协议，使任务能按认知事件类别声明类型安全、可持久化且可确定性回放的 `ignore` 规则；属性条件只能引用对应事件 Schema 明确开放的字段。
- [ ] 为属性条件定义受限的声明式比较协议，至少覆盖相等、集合包含和数值阈值，不允许通过任意脚本读取世界私有状态。
- [ ] 在感知与角色定向路由完成后、触发熔断前，对每个目标角色逐条执行当前任务的 `ignore` 规则；声音规则使用距离衰减后角色实际接收到的音量，而不是声源原始音量。
- [ ] 以轨道覆盖合并 `ignore` 结果：只有匹配规则覆盖完整的 `{HEAD, BODY}` 才忽略事件；独立任务分别贡献其占用轨道，同步任务的唯一规则集一次覆盖两轨，空任务不贡献覆盖。
- [ ] 将任务自然完成、失败和客观不可继续保留为不可被任务 `ignore` 的引擎生命周期信号，确保非空任务最终一定触发决策。
- [ ] 将三类人物认知视觉事件、`visible_object_state_changed`、角色互动、瞬时 `speak` 声音、持续声音出现/内容/消失和任务结果接入熔断触发接口；视觉移动累计仍通过 `move` 动作回执返回，不把每个原始视觉采样伪造成事件。
- [ ] 第一个未被完整忽略的触发只锁存 `freezePending`；引擎继续完成当前 Tick 剩余的确定性阶段，收集该 Tick 已提交的全部触发，然后在推进下一 Tick 前生成原子检查点并熔断。不得在 Tick 管线中途暴露半完成状态，也不得因批处理额外推进 Tick。
- [ ] Tick 是唯一合并窗口，不使用现实时间 debounce、延迟等待或模型响应窗口吸收更多事件。
- [ ] 进入熔断后分别调用相关角色当前 active operation 的只读熔断处理；每个 `callId` 至多生成一次中间回执，多槽位调用不得按槽位重复调用，两个独立调用按 `HEAD`、`BODY` 规范顺序排列。
- [ ] 对每个受影响角色，把操作中间回执放在触发列表之前，再将同一 Tick 的全部未忽略触发按权威全局事件序号稳定排序；最后从封口后的冻结检查点生成并追加一份该角色私有的 `perception_now`。回执和触发内容保持独立，不做语义合并、摘要或去重。
- [ ] `perception_now` 使用相对方位而非世界坐标，包含由冻结 `worldTick` 派生的当前游戏日与时分、当前可见类别、可见角色行为与 `externallyVisible` 外观、可见对象公开状态和本轮当前可选 operation；它是当前状态快照而非事件，不暴露原始 Tick，不携带 `callId` 或来源事件，不进入触发过滤，也不得导致递归熔断。
- [ ] 同一 Tick 受影响的所有角色进入同一个世界决策周期，但每个角色只收到经过自身感知和 `ignore` 过滤的私有批次，并各自发起一次思考；不得把其他角色的不可见触发泄漏进其输入。
- [ ] 同一 Tick 对事件逐条执行双轨覆盖过滤；所有事件都被完整覆盖时继续运行，只要存在未被完整覆盖的事件就熔断一次，并只把这些未忽略事件按稳定顺序交给角色。
- [ ] 在熔断检查点记录本轮输入截止序号；截止后到达的异步结果使用独立、持久化且单调递增的接收序号进入待处理队列，不得改变已封口的角色请求。
- [ ] 放行当前决策后，在世界推进下一个 Tick 前按接收序号处理队列；同一冻结 Tick 的多个有效结果稳定合并为下一次熔断，避免逐个重启模型请求。
- [ ] 对已经被本轮决策替换或取消的操作，其迟到结果只能写入审计，不得产生操作结果消息或世界效果；仍被 `continue` 的操作可以在同一冻结 Tick 提交已就绪结果。
- [ ] 将输入截止序号、待处理队列和迟到结果处置纳入快照、恢复及回放，保证同一记录产生相同的连续决策顺序。
- [ ] 扩展冻结和批处理测试，逐项断言当前 Tick 管线完整提交、下一 Tick 不推进、同 Tick 多触发不丢失也不去重、多角色输入彼此隔离、回执与触发排序稳定，以及所有角色、对象、需求、随机数和任务在思考期间保持不变。
- [ ] 增加视觉边沿与公开行为契约测试：拒绝缺失 `publicBehavior` 的 operation；验证显式 `hidden`、单轨组合顺序、多槽位只投影一次、行为开始/结束各触发一次、内部阶段和逐 Tick 进度不触发、`speak`/`recall` 私有载荷不泄漏，以及快照恢复和回放得到相同投影。场景同时覆盖厕所使用中有人进入视野会熔断且原任务保持、人物离开不熔断、重新进入再次熔断、完成后的公开外观变化触发一次、同 Tick 多人出现只形成一个世界决策周期。
- [ ] 增加物体状态边沿测试：已声明的可见公开变化只触发一次，未声明变化和连续数值进度不触发，不可见对象不投递，私有字段既不参与匹配也不进入载荷；同一提交在恢复和回放中产生相同事件，多个同 Tick 边沿仍只形成一个世界决策周期。
- [ ] 增加指定作用角色的 operation 契约测试：缺失、非法或运行中偷换 `targetCharacterId` 均被拒绝；开始、执行中、熔断、失败和取消不发送定向互动事件；正常完成时效果、发起者成功回执和目标互动事件同时提交，模拟提交失败时三者全部回滚；互动事件只进入锁定目标的上下文并只请求目标思考；目标在完成后看得见发起者时收到公开姓名，看不见时只收到匿名描述且任何模型输入字段都不泄漏真实 ID；发起者不收到重复互动事件，无视觉或听觉依据的旁观者不知情；`speak` Schema 不存在作用角色参数并仍按听觉范围产生一对多投递，恢复和回放保持相同接收者与身份裁剪结果。
- [ ] 增加时间与声音接口测试：每份 `perception_now` 的游戏日和时分都与冻结 Tick 一致且不含原始 Tick，时间自然变化不触发思考；`speak` 只接受“小声、正常、大声”，其他档位和任意数值都无法建立调用；每条已投递声音都携带真实角色、对象或环境来源及接收者视角的大致方位，接收者看不见声源及内容被距离模糊时来源和方位仍保留，角色转向后产生的下一声音事件使用新方位，范围外角色收不到内容、来源或方位，所有角色可见字段都不含世界坐标。一次 `speak` 完成只产生一个瞬时声音批次且不产生开始/消失事件；持续环境音只在进入可听、产生新内容和离开可听时产生事件，单纯方向、距离和接收音量变化不触发思考。

**完成门槛：** 外来事件能让相关角色在冻结状态下重新决策，但在决策放行之前没有任何世界事实或原任务发生改变。

### 阶段 6：项目持有的日内对话上下文

- [ ] 为每个角色建立可持久化、可恢复、可回放和可分支的日内对话上下文。
- [ ] 为角色增加带稳定目标 ID 的可持久化长期目标和短期目标；它们属于稳定认知，不与当前 `HEAD/BODY` 执行任务混为同一状态。
- [ ] 定义 `goalUpdates` 的严格补丁协议，支持新增、修改、明确完成和放弃，并校验调用者只能修改自己的目标、目标 ID 存在性及单次补丁内部一致性。
- [ ] 在决策放行时原子提交 `goalUpdates` 与双轨任务选择；任一目标补丁或任务选择无效时整份决策拒绝，不允许只提交其中一部分。
- [ ] 任务自然完成、失败或被替换时不得隐式改写目标；新的角色决策可以根据任务结果明确更新目标。
- [ ] 保存角色实际经历的语义对话轮次：角色决策、`operation_call`、`operation_result`、`perception_event`、`perception_now` 以及目标更新；`recall` 与 `move` 使用同一操作消息类型。
- [ ] 只有通过 Schema 与完整预检的最终决策才能追加到角色日内上下文；被拒绝的模型输出、校验反馈和纠错轮次只保存在模型调用及技术错误审计中，重建上下文和睡眠整理都不得读取它们。
- [ ] 只有已声明 `domain_failure` 的公开结果可以作为失败 `operation_result` 进入日内上下文；技术错误详情、堆栈、插件私有状态和内部标识只写技术审计，提示词组装与睡眠整理不得读取。
- [ ] 扩展厂商无关的消息协议，至少表达系统内容、角色决策、`operation_call`、`operation_result`、`perception_event` 和 `perception_now`，不再局限于当前的 `system/user` 两种消息。
- [ ] 要求每个 `operation_result` 引用已存在且属于该角色的 `callId`；自发感知只能写为 `perception_event`，协议层拒绝无调用来源的伪工具结果。
- [ ] 决策中的 `replace` 为对应 operation 创建新 `callId`；`continue` 只引用现有调用而不产生新的 `operation_call`。一个调用无论完成、失败还是取消，都只能写入一条关闭该 `callId` 的终态结果。
- [ ] 在每次模型请求的结构化 `activeTasks` 中投影各槽位当前引用的 `callId` 及操作状态；多槽位调用只存一份详情并列出其 `taskSlots`，不得向模型伪造成两个独立任务。
- [ ] 在 operation 候选、`operation_call` 和 `activeTasks` 中投影结构化执行时间语义：明确显示固定或不确定；调用建立后显示 `startedAtTick`，固定调用额外显示锁定的 `totalTicks`，不得给不确定调用伪造预计完成 Tick。
- [ ] 将操作生命周期产生的正常、失败、取消终态结果和可选熔断中间回执按实际发生顺序写入对话；终态结果信封不可省略，明确声明无熔断回执的操作则不得制造中间占位消息。
- [ ] 将 `move` 的 `nearby` 作为工具式动作结果追加到对话；每个认知熔断另将统一生成的最新 `perception_now` 追加到本轮末尾。两者都不得写入系统提示词或覆盖旧经历。
- [ ] 三类人物认知视觉事件、`visible_object_state_changed`、瞬时 `speak` 声音、持续声音出现/内容/消失和角色互动以 `perception_event` 投递，并在未被当前双轨任务完整忽略时触发一次思考；未声明的对象公开变化、其他连续视觉状态、持续声音的方向/距离/接收音量变化和人物离开视野不追加伪事件消息。
- [ ] 重建上下文时严格保持世界 Tick 与事件序号顺序，并对重试、重复投递和恢复建立幂等规则。
- [ ] 系统提示词按稳定顺序组装：最上方是压缩后的长期记忆、长期目标和短期目标，紧随其后是角色自己的完整衣物与身体状态；核心规则及输出约束不得打乱这两个区块的相对顺序。
- [ ] 将区域级空间知识与长期记忆和目标一起放入稳定认知区块，只渲染区域相对关系、用途、主要设施和能力，不投影内部坐标、寻路格或观察流水账。
- [ ] 环境信息只出现在日内对话内容中，不复制到系统提示词。
- [ ] 模型适配器只消费组装结果；更换或删除供应商侧会话后，仍能仅凭本地数据重建同一次请求。
- [ ] 由各模型适配器把本地消息类型投影到供应商支持的输入格式；供应商缺少自定义事件角色时，把 `perception_event` 渲染为带严格事件信封的普通输入，但不得修改本地权威类型或伪造工具调用关系。
- [ ] 建立消息因果测试，覆盖主动操作调用/结果配对、自发事件无 `callId`、指定作用角色的互动事件只在成功完成后进入目标上下文且看不见发起者时保持匿名、`speak` 的声音按实际听见者分别进入上下文并标注声源、`perception_now` 包含派生时间但无 `callId` 或原始 Tick 且不触发事件、回执/事件/当前快照稳定排序、恢复重建和不同供应商投影。

**完成门槛：** 从任意检查点恢复后，角色下一次看到的系统内容和日内对话顺序与未中断运行一致。

### 阶段 7：Token 预算与疲惫压力

- [ ] 用真实 Token 计数替换当前按字符限制的提示词预算，并按实际目标模型选择对应计数策略。
- [ ] 定义约 `200k` 的注意力安全预算，同时为模型输出、工具调用和协议开销预留空间。
- [ ] 分别计算系统提示词、日内对话、工具定义和预留输出的 Token，占用数据必须可观测。
- [ ] 定义清醒时间压力与 Token 压力的归一化方式，再按暂定 `0.6 + 0.4` 权重组合为疲惫压力。
- [ ] 将连续清醒 `43,200 ticks`（3 个游戏日）作为时间压力达到 `1.0` 的暂定基线，并将组合疲惫强制昏睡阈值暂定为 `0.6`；Token 技术硬上限保留独立强制入口。
- [ ] 保留独立技术硬上限，确保任何请求都不会超过目标模型实际支持的输入边界。
- [ ] 达到警戒线时让疲惫成为角色可感知状态；达到强制阈值时触发原地昏睡流程。
- [ ] 将权重、软阈值、硬阈值和预留预算集中配置，并通过长时间仿真校准，不散落硬编码。
- [ ] 执行长时间仿真校准：验证暂定权重 `0.6 + 0.4`、清醒基线 `43,200 ticks`、强制昏睡阈值 `0.6` 在典型玩法节奏下是否让角色在合理时机感到疲惫与昏睡；把校准后的曲线与阈值写回集中配置，并用测试锁定校准结果防止回退。

**完成门槛：** 能解释任一角色当前疲惫由多少清醒时间压力和多少 Token 压力构成；请求永远不会越过技术硬上限。

### 阶段 8：睡眠生命周期与记忆整理事务

- [ ] 增加床和“上床睡觉”入口，启动一份同时占用 `HEAD/BODY` 的同步睡眠任务；该任务只有一个共享实例、进度和生命周期。
- [ ] 增加压力超限的原地昏睡入口，并记录其原因；主动睡眠与强制昏睡复用同一睡眠、整理和逻辑唤醒状态机。
- [ ] 分别从入睡时的时间疲惫和待整理上下文规模确定 `timeRecoveryTicks` 与 `consolidationTicks`，再以 `max(minimumSleepTicks, timeRecoveryTicks, consolidationTicks)` 计算睡眠时长和 `wakeTick`；没有未忽略事件时睡眠任务持续执行，其他角色与世界继续运行。
- [ ] 确定 `timeRecoveryTicks` 与 `consolidationTicks` 的具体换算曲线以及 `minimumSleepTicks` 的数值，全部写入规则集；三者取 `max` 的组合机制保持不变，不因数值调整而改变并发语义或唤醒时机。
- [ ] 将睡眠期间的后台记忆整理建模为可恢复任务，明确开始、成功、失败、重试和提交状态。
- [ ] 整理提前完成时只持久化为待提交结果，不得让角色早于 `wakeTick` 醒来，也不得提前切换其认知周期。
- [ ] 整理结果未成功持久化前不得清空旧日内上下文；到达 `wakeTick` 时原子提交整理结果、切换到下一认知周期并唤醒角色。
- [ ] 到达 `wakeTick` 而整理仍未完成或未成功持久化时触发世界级熔断，世界保持在该 Tick；整理完成后仍从同一 `wakeTick` 唤醒，不把模型 API 的现实延迟换算成额外游戏 Tick。
- [ ] 为睡眠任务声明事件 `ignore` 规则，例如忽略接收音量低于配置阈值的声音；匹配在角色定向感知结果上执行，不为睡眠另建特殊事件等级或唤醒分支。
- [ ] 确定睡眠 `ignore` 的具体阈值（例如接收音量低于哪一档的声音被忽略），写入规则集并按事件属性匹配；不为不同角色单独建模睡眠深度。
- [ ] 未被睡眠任务忽略的事件只触发统一熔断，睡眠任务和整理事务在决策前保持不变；双轨 `continue` 后继续原睡眠，双轨原子替换后才提前结束睡眠。
- [ ] 替换睡眠任务时原子作废本次未提交的整理任务和暂存结果，保留完整旧上下文；按实际睡眠 Tick 恢复时间疲惫，Token 压力保持不变，并用整理周期 ID 拒绝迟到结果。
- [ ] 为主动睡眠、强制昏睡、同步任务双轨一致性、整理提前完成、逻辑唤醒点尚未完成、事件属性忽略、未忽略事件后继续睡眠、主动替换睡眠、迟到结果、保存失败、恢复和跨天建立场景测试。

**完成门槛：** 无论正常运行、崩溃恢复还是整理重试，日内经历都不会丢失或重复归档，角色只会看到完整的上一周期或完整的下一周期。

### 阶段 9：睡眠记忆整理

- [ ] 设计专用整理输入，只使用该角色实际拥有的上一周期保留记忆、只读目标、上一周期区域语义地图和本周期日内对话；本周期内的 `recall` 结果因已进入日内对话而按相同规则参与整理。
- [ ] 设计严格的结构化输出：逐条 `retainedMemories`、逐条 `archivedMemories` 及完整的下一周期区域语义地图；输出 Schema 不接受任何目标修改字段。每条普通记忆的重要性只能是 `critical | high | normal | low`，并包含判断理由与来源引用。
- [ ] 对整理请求前后的目标状态做事务断言，确保整理成功、失败和重试都不能改变长期或短期目标。
- [ ] 将本次 `retainedMemories` 作为下一周期唯一的普通保留记忆集合；上一周期条目不得自动复制，必须明确重新保留、合并压缩或转入 `archivedMemories`。
- [ ] 不对整理输出执行跨条目或跨周期的语义去重；模型重复输出的保留与归档内容按独立条目接受，只做 Schema、来源权限和事实约束校验。
- [ ] 拒绝模型给出的任意数值重要性、删除日期或删除决定；这些字段只能由程序根据离散等级和集中配置派生。
- [ ] 为每条结果保留来源事件、形成 Tick、整理周期、重要性等级和判断依据，保证记忆可追溯。
- [ ] 将空间知识建模为按稳定区域 ID 索引的概略描述，至少表达区域名称、与其他已知区域的相对位置、用途、主要持久设施及其能力；区域 ID 只用于程序合并与校验，给模型的正文不暴露坐标。
- [ ] 禁止区域语义地图包含精确坐标、路径格序列、每次经过的观察记录，以及门的开关、人物位置、临时占用等短暂状态；这些信息只留在对应日内经历或即时感知中。
- [ ] 每次整理必须覆盖所有上一周期已知区域，并可依据本周期真实探索新增或修正区域描述；无来源的新区域、设施或能力以及无依据丢失旧区域都应拒绝提交并重试。
- [ ] 禁止整理模型补造角色未感知的事实；对无来源、冲突和格式错误的结果拒绝提交并重试。
- [ ] 将保留记忆压缩后放入下一周期系统提示词；不再把上一周期完整日内对话继续携带。
- [ ] 建立长日记、重复经历、矛盾信息、空间连续性和失败恢复测试。

**完成门槛：** 睡眠后上下文明显缩小，同时角色仍记得关键人物、目标、重要经历和大致空间结构。

### 阶段 10：归档记忆数据库与 `recall` 工具

- [ ] 扩展时间线存储接口和 SQLite Schema，保存按世界、分支、角色和整理周期隔离的逐条归档记忆。
- [ ] 存储记忆正文、来源、形成 Tick、归档 Tick、重要性及检索所需索引；当前强度由归档年龄和集中配置确定，不为 `recall` 维护会影响衰减的专用最后回忆状态。
- [ ] 在程序配置中为 `critical | high | normal | low` 映射固定初始强度和 `halfLifeDays`，并设置统一删除阈值；模型输出不得绕过或修改该映射。
- [ ] 为四档重要性确定具体初始强度、`halfLifeDays` 与统一删除阈值，写入集中配置；取值需保证 `critical` 记忆在典型游戏时长内不会被自动删除，而 `low` 记忆会在合理天数内衰减消失。
- [ ] 在跨天边界由程序按 `initialStrength * 2 ^ (-archiveAgeDays / halfLifeDays[importance])` 直接重算强度；低于阈值时由程序实际删除，不在跨天流程中调用模型。
- [ ] 保证跨越多个日期边界的一次性计算与逐日执行得到相同强度和删除结果，避免连续浮点乘法造成恢复与回放漂移。
- [ ] 实现角色专属的 `recall` 工具，只检索调用者自己的归档，不允许跨角色读取。
- [ ] 把 `recall(query)` 注册为占用 `HEAD` 的统一语义操作，而不是模型网关内的嵌套工具循环；其查询文本通过操作参数 Schema 校验并随操作调用持久化。
- [ ] 为归档正文建立 SQLite 全文索引和向量索引，通过稳定记忆 ID 合并两路对同一记录的命中；内容相似但 ID 不同的归档记忆必须作为独立候选保留。
- [ ] 定义编码器抽象和模型锁，至少记录编码器 ID、精确版本、向量维度、归一化方式及模型文件身份；模型切换必须显式重建向量索引。
- [ ] 确定本地编码器的最终运行后端与索引迁移方案：需评估跨机器结果一致性（回放读取记录不重算，但新分支上重新检索的结果应当可复现）与部署依赖成本；索引重建必须在编码器 ID、版本或模型文件身份变化时自动触发，并对旧索引做明确失效而非静默混用。
- [ ] 将归一化后的语义相似度、关键词匹配度和当前记忆强度组合为最终排序；不得再单独加入时间或重要性，避免重复加权。
- [ ] 确定三项排序因素的具体权重并写入规则集；权重需经过检索质量仿真校准，不一次性拍定后不再调整。
- [ ] 在操作开始时锁定归档库版本、编码器版本和索引版本，分配稳定调用 ID 并异步发起检索；`recall` 在结果返回前持续占用 `HEAD`，不预先计算逻辑完成 Tick。
- [ ] 让 `recall` 通过通用时间接口明确解析为 `indeterminate`；实际结果就绪是其完成信号，不再依赖专用的时长例外字段。
- [ ] `recall` 执行期间占用 `HEAD`，独立 `BODY` 任务照常推进；若其他未忽略事件先触发熔断，`recall` 不返回中间结果，选择 `continue` 后保留原进度，选择 `replace` 后作废待返回结果。
- [ ] 世界处于 `RUNNING` 时，检索结果实际返回所在的 `worldTick` 即操作完成 Tick；在该 Tick 持久化结果、完成操作并触发世界级熔断，不使用固定时长或 Token 时长公式。
- [ ] 检索结果在世界已经熔断后返回时只进入封口后的异步队列；本轮选择 `HEAD continue` 后在同一冻结 Tick 完成并触发下一次熔断，选择 `HEAD replace` 后丢弃角色可见结果但保留调用审计。
- [ ] 将 `recall` 调用 ID、开始 Tick、实际完成 Tick、编码器与索引锁、查询、最终结果和错误完整持久化；历史恢复与回放读取该记录，不重新执行 GPU 检索。
- [ ] 从旧快照创建新分支时重新执行尚无已记录结果的检索，并明确允许新分支因实际返回延迟不同而在后续 Tick 时序上分歧。
- [ ] 正常完成时按规则集的 `maxReturnTokensPerOperation = 8000` 截断并返回工具结果，随后按所有非空操作的统一规则触发熔断；重复回忆通过模型再次选择新的 `recall` 操作实现，不建立专用嵌套循环或调用次数计数器。
- [ ] 通过阶段 6 的通用工具消息协议把 `recall` 调用与结果加入日内对话；不得因本次读取额外修改归档记忆，后续睡眠整理直接从上下文看到该结果。
- [ ] 对隔离性、衰减、删除、重复内容独立存取、重复调用、恢复、分支和无结果场景建立测试。

**完成门槛：** 角色能按当前意图找回相关旧记忆；旧记忆按确定性规则衰减和删除；任何角色都无法检索他人的私有记忆。

### 阶段 11：听觉与其他实时感知

- [ ] 在阶段 5 先预留统一听觉输入接口和声音事件载荷，本阶段再实现完整传播算法。
- [ ] 优先实现 `speak` 的瞬时声音路径：一次正常完成的说话在完成 Tick 只计算一次传播并生成一个多接收者事件批次，不创建持续声音实例，不产生开始或消失事件；失败或取消不广播尚未成功完成的说话内容。
- [ ] 要求每个声音定义或发声调用绑定权威声源：角色声音绑定发声角色 ID，家具和物体声音绑定对象实例 ID，环境声音绑定稳定环境来源 ID；渲染为角色可见事件时使用对应公开名称，不允许模型伪造或改写来源。
- [ ] 在每次声音实际投递时，根据该 Tick 的声源位置、接收者位置和接收者朝向计算前方、左侧、右后方等大致相对方位；同一声音对不同接收者可以得到不同方位，持久化投递结果供恢复和回放直接使用，模型输入不暴露世界坐标。
- [ ] 为环境声定义固定声源强度；角色执行 `speak` 时只从“小声、正常、大声”三档选择，并由世界锁定的规则映射为声源初始强度。所有声音使用统一衰减规则，实际清晰、模糊和不可听范围从声源强度与接收阈值计算，不接受任意数值音量或单独手填每档传播半径。
- [ ] 在统一距离衰减之上叠加**墙与门的遮挡衰减**：衰减系数写入规则集，静态墙的遮挡可预计算，动态门在传播时实时叠加；同一声源在门开与门关时须得到不同的接收强度。明确**不为区域设置背景噪声基线**，听清程度只由声源强度、传播衰减（含遮挡）与接收阈值三者派生。
- [ ] 建立遮挡传播测试：同一三档音量下，验证无遮挡、隔墙、隔关闭的门三种情形各自得到确定且依次递减的接收强度；验证开门后传播结果立即变化；验证保存恢复与回放后遮挡结果不漂移。
- [ ] 按最终接收强度分为完整听见、随机模糊并标注“距离太远听不清”、完全不投递三段；前两段都保留权威声源和相对方位，第三段不泄漏声音存在、来源或方位。
- [ ] 使用世界确定性随机源进行模糊，保证保存恢复和回放结果一致。
- [ ] 建立三档传播边界测试：同一位置和遮挡条件下验证“小声、正常、大声”各自按锁定配置得到确定的接收强度与投递结果；验证档位映射、衰减和阈值在快照恢复与回放后不漂移。
- [ ] 后置实现持续环境声：对每名角色维护该声源当前是否可听；进入可听范围时投递声音出现，声源产生新内容时投递内容，离开范围或声源结束时投递声音消失，并按阶段 5 的规则触发熔断。
- [ ] 持续声音仍可听时，声源或接收者移动、转向导致的方向、距离和接收音量连续变化只更新状态，不投递新事件；下一次真正的内容事件必须使用当时最新的传播结果。另行处理同源持续声音的去重、遮挡规则和多人同时发声。
- [ ] 对同一次 `speak` 的每个实际听者独立生成投递结果：完整听见者得到完整内容，模糊听见者得到确定性模糊内容，不可听见者不获得任何事件；不得另外建立“说话对象”通道或绕过环境传播。

**完成门槛：** `speak` 说完后只产生一次瞬时声音批次并让实际听见的角色反应；后续持续环境音只在进入可听、产生内容和离开可听时通知。所有已投递结果都标明相同权威来源及各接收者自己的相对方位，并能确定性重放完整、模糊和未投递三种结果。

### 阶段 12：完整插件化物品与家具交互系统（后置）

- [ ] 基于阶段 3 已建立的物品定义、实例、容量与归属内核，把总上限 9 单位的随身容量规则扩展到所有物品类型；仍不建立固定格子，也不把 9 解释为物品件数上限。
- [ ] 要求所有物品定义声明容量占用；拾取、转移和生产完成后的随身物品总占用不得超过角色容量，并与阶段 3 的衣服物品使用同一计算器。
- [ ] 扩展阶段 3 的物品注册协议，使其达到与家具定义体系一致的完整插件能力，包括显示信息、公开状态、插件私有状态和版本锁；不得改变已有定义或实例身份语义。
- [ ] 在既有 `carried | worn` 归属上增加世界位置、容器或其他合法归属，并继续保证每个物品实例恰好只有一个归属，禁止复制和悬空所有权。
- [ ] **明确不支持容器嵌套**：只有角色与家具可以持有物品，物品不能容纳其他物品，容量计算因此不递归。物品实例的合法归属只有三类——角色、家具、世界坐标，任何时刻恰好属于其中之一。
- [ ] 定义物品自身可提供的操作与任务候选接口，使角色能够检查和操作自己携带的物品；具体操作由物品插件声明。
- [ ] 定义“携带物品 → 家具”的交互协议。物品定义通过稳定交互标识声明自己可参与哪些家具交互，以及参与时提供的公开输入信息。
- [ ] 扩展家具协议，让家具显式注册对应交互标识的处理方法；没有家具处理方法或没有物品侧参与声明时，不生成该交互候选。
- [ ] 交互请求支持一次指定多个具体物品实例，并至少包含执行角色、目标家具、交互标识和所选物品实例列表。
- [ ] 家具处理方法对整组物品执行一次预检，包括物品确由角色携带、实例不重复、物品状态允许参与、组合与数量符合家具规则，以及家具当前状态允许处理。
- [ ] 家具处理方法只提出效果，统一裁决层原子提交物品消耗、物品转换、新物品产出、归属变化和家具状态变化；任一校验或效果失败时整组交互不得部分生效。
- [ ] 将携带物品与家具的交互建模为单个 `BODY` 语义操作；内部可以处理多个物品，但不能被拆成多个会留下半成品的独立提交。
- [ ] 让生产类操作只在正常完成事务中创建物品；熔断中间回执不得提前创建产物。炒菜操作以此规则接入。
- [ ] 生产操作的产物规则（配方）写在**版本化内容定义**中，插件只负责按当前权威状态查表并生成对应产物；产物必须先是真实的世界效果（生成物品实例），再作为 `result` 告知模型，不得只返回描述性文本冒充产出。同一操作在不同输入下产出不同结果时，差异必须来自查表而非硬编码分支。
- [ ] 禁止跨越语义边界的自动串联：生产操作不得在其内部自动执行「取食材」「放食材」等其他语义操作，后者由角色分次决策执行，每次结束后触发熔断。这不排斥单个语义操作接受多个物品实例作为输入（见第 403、406 条）。
- [ ] 对拾取、放下、转移、消耗、转换、生成和销毁执行原子容量与所有权校验，失败时不得留下半提交状态。
- [ ] 抛弃操作使物品成为带世界坐标的**独立实体**，参与现有 FOV/LOS 计算，不作为某个房间级容器内的抽象条目；落点固定为抛弃时角色当前所在格，不按朝向推导，也不做兜底格查找。
- [ ] 销毁不是通用能力：由物品插件在自己的 `interactions` 中可选声明，核心不注册可在任意对象上调用的通用销毁操作。
- [ ] 角色之间的物品转移采用**两步协议**：发起方的 `give` 在正常完成时才写入「待转移」状态并让目标角色感知，目标角色必须自己决策执行 `accept` 才完成归属转移；引擎不得在 `give` 完成时自动转移归属，也不得在 `give` 开始或执行期间要求目标角色响应。「待转移」写入物品实例状态并随快照持久化。
- [ ] 将物品实例、携带容量、随身物品集合和插件私有状态纳入领域事件、快照、恢复、回放和分支。

### 4.1 已澄清：不属待定项的伪问题（2026-09-04）

原清单曾把「装备、公开可见性、销毁」列为物品规则，这是**摘要表述偏差**，不是真实待定项。物品插件只有能力与可执行操作，没有类别属性：

- `ObjectDefinition`（`packages/plugin-sdk/src/object/object-definition.ts`）只声明 `movement` / `vision` / `traversal` / `occupancy` 四种能力与 `interactions` 列表，不存在 `equippable` / `visible` / `destroyable` / `droppable` 之类的类别字段。这是红线「插件只认能力，不认类别」的直接体现。
- **装备**是 operation，不是物品属性：`wear` / `undress` / `adjust_clothing` 由物品或家具插件以 `InteractionDefinition` 提供候选，核心不注册通用换装操作（见阶段 3 相应条目）。
- **可见性**属于角色，不属于物品：`externallyVisible` / `internallyHidden` 是角色自身的结构化外观分区，配合感知读取权限；观察者只读外见分区。
- **掉落位置与销毁**由角色执行对应 operation 时的状态或 operation 自身决定，不写在物品定义上。

上述各项的通用协议细节（落点规则、转移步骤、嵌套支持、销毁能力）已于 2026-09-04 全部拍板，写入约束 71、72。

**operation 是统一概念**：移动、说话、使用家具、使用物品、`recall` 全部是同一个 `OperationContract` 的实现，共享 `taskSlots` / `parametersSchema` / `eventIgnore` / `publicBehavior` / `domainFailures` / `resultSchema` 与 `resolveDuration` / `fail` / `cancel` / `fuse` 生命周期。物品交互不是平行体系——`InteractionDefinition extends OperationContract`，只是在共同契约上多挂了 `id` / `displayName` / `trigger` / `canStart` / `start` / `complete`。依据：阶段 1 第 126 条「所有游戏内操控统一建模」、`packages/plugin-sdk/src/operation/operation-contract.ts` 的 `assertOperationContract` 加载期校验。见约束 76。

**补偿效果协议已定稿**：持续效果 operation 在替换、失败与正常完成时的补偿规则，其全局协议已在阶段 1 第 151、152 条定稿——禁止回滚已提交效果，恢复只能通过新的补偿效果表达，未提交的完成效果直接丢弃，且「旧调用退出 + 补偿效果 + 占用释放 + 终态结果」是一个原子终止事务。`InteractionDefinition` 的 `fail()` / `cancel()` 已提供补偿效果的提交入口（返回 `InteractionLifecycleProposal`）。剩余的是逐个 operation 在实现时声明具体补偿内容，不是架构待定项。

## 附录 A：operation 设计案例（2026-09-04 拍板记录）

以下案例用于理解约束 70-78 的意图。**施工以约束条目和各阶段 TODO 为准**，案例只是说明，不额外增加约束。

### A.1 「做西红柿炒蛋」——不存在复合 operation

**错误做法**：定义一个 `cook_tomato_egg` 操作，内部自动完成「从冰箱拿蛋 → 走到灶台 → 放蛋 → 放番茄 → 开火」。这违反约束 74 与阶段 1 第 137 条：不同语义操作不得静默串联。

**正确做法**：只存在三个独立 operation，由角色分次决策执行。

1. 鸡蛋的 `put_into`——target 声明 `requiredCapabilities: ["heating"]`，调用时角色填具体灶台实例。
2. 番茄的 `put_into`——同一个 operation 定义，不同实例。
3. 灶台的 `cook`——`canStart` 检查锅内是否有食材；不满足时返回已声明的失败码并在 `summary` 里说明缺什么。

每次执行结束都触发熔断，由角色重新决策。角色怎么知道要先放食材？读灶台的说明书（A.3）。

**产物**：`cook` 的 `complete()` 提交「销毁食材实例 + 生成产物实例」的效果，再返回 `result` 描述产物。配方（蛋+番茄→西红柿炒蛋）写在版本化内容定义里，插件只查表；同一操作在不同输入下产出不同结果时，差异必须来自查表而非硬编码分支。

### A.2 「把东西给另一个人」——两步转移

场景：Alice 把钥匙给 Bob。

1. Alice 执行 `give`（钥匙物品声明的 operation，target 声明需要角色）。`canStart` 校验 Alice 持有钥匙、Bob 在范围内、Bob 有剩余容量。
2. `give` **正常完成**时，提交 `replace_object_state` 把「待转移」写进钥匙实例自己的状态：`pendingTransfer = { toAgentId, offeredAtTick, expiresAtTick }`，并用 `emit_perceptible_result` 让 Bob 感知。此时**归属未变**，钥匙仍属于 Alice，只是被锁定。
3. Bob 感知后自己决策，执行 `accept`（target 是那把钥匙实例）。`canStart` 校验 `pendingTransfer.toAgentId` 是自己。
4. `accept` 正常完成时，原子提交归属转移并清除 `pendingTransfer`。

Bob 拒绝或不响应：钥匙保持「待转移」直到过期。**引擎不得在 `give` 完成时自动转移归属**——这与阶段 1 第 62 条「只有正常完成才向目标角色发送互动事件」是同一条原则，也与第 137 条「下一步由角色重新决策」一致。

「待转移」写进物品实例状态，因此自动随快照持久化，不需要新建世界实体类型。

### A.3 「read 说明书」——渐进式披露

场景：角色第一次遇到冰箱。

- 系统提示词声明存在 `read` 工具，与 skill 同构——用法不预先注入上下文，需要时才读。
- 角色调用 `read(objectType: "home.refrigerator")`，拿到冰箱插件在定义中声明的静态说明书，例如「可以存放食物（`stock`）、取出食物（`use`）、设置模式（`configure`，需 mode 参数）」。
- 说明书**只写静态用法**，不写「现在能不能用」——可用性一律由 `canStart` 依据权威状态实时判定。因此说明书不会因世界波动而过期，也无需记录「这个角色读过哪些实例」。
- 说明书按**类型**取，不是按实例：所有 `home.refrigerator` 实例共享同一份说明书，不占额外存储。

### A.4 「鸡蛋放进锅里」——operation 定义在宿主内部

**前提**：operation 一律定义在宿主对象（物品或家具）的 `interactions` 内，**不存在脱离宿主独立存在的 operation**。因此目标需求分两种：

- **宿主自身的 operation**（如锅的 `cook`）：目标就是宿主自己，由候选生成时绑定的宿主实例确定，不需要额外声明。
- **作用于外部对象的 operation**（如鸡蛋的 `put_into`）：才需要声明目标需求。

```
锅（家具）：  tags: ["kitchen", "appliance"]           类别，不参与匹配
              capabilities: ["heating", "container"]    能力，参与匹配
              interactions: [cook, ...]                 煮汤属于锅，目标即锅本身

鸡蛋（物品）：capabilities: ["food"]
              interactions: [put_into, ...]
              put_into 的 target: { kind: "object", requiredCapabilities: ["heating"] }
```

**后果对比**：以后新增电饭煲，只要它声明 `capabilities: ["heating"]`，鸡蛋的 `put_into` 立刻能把它当作目标，鸡蛋的定义**一行不用改**。若写成「鸡蛋只能放进 `pot`」这种类别写法，则每加一个新容器都要回头改所有物品的定义，长期耦合成一团。

`tags` 与 `capabilities` 严格分离：类别只用于展示与归类，**不参与匹配**；匹配一律走能力。这是红线「插件只认能力，不认类别」在操作目标层的落实。
